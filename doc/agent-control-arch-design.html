01 总体分层（框架 / 护城河 / 能力 + MCP）

框架态核心：三层栈（L3 框架 / L2 护城河 / L1 能力）物理边界清晰。自研能力以 function_tool 插件承载、外部系统以 MCP 接入，二者在 L1 层完全平级；内核退化为「配置 + 钩子注册中心」。

03 单次任务 ReAct 闭环（框架原生 + 钩子）

框架态（已落地）：ReAct 循环由 OpenAI Agents SDK 原生驱动（omni_core/brain/sdk_loop.py 的 Agent + Runner.run），内核不再手搓；手搓的 _run_inner 已标记废弃、主路径不再调用。L2 通过框架原生机制挂接：StopAtTools（task_done / verify / escalate 收尾）、RunHooks（每步结果 → 世界模型 / 轨迹）、分块 max_turns（预算与升级检查点）。完成判定仍走 backend.verify_done，区分「页面变了」与「目标达成」。

图 N3 · 单次任务 ReAct 闭环（框架态，已落地）。循环由 SDK Runner 驱动；Verify / 收尾 / 升级通过 StopAtTools + RunHooks 挂回 L2；失败重试与自愈由护城河决策（C4）。
为何 Verify 是钩子而非内核步骤（C4）：经典 Computer-use 翻车 = 「点了 → 页面变了 → 以为完成」。框架态保留两层校验：① 显式 verify 钩子：spec.expected / done_when 命中 → 直接 DONE（不调大模型）；② task_done 门控：大模型调 task_done 时强制 verify_done，通过才接受。verify 逻辑在 L2（护城河），内核循环不感知其实现。
感知工具三角（延续）：observe（u2 层级树 text，快）/ ocr_screenshot（EasyOCR GPU）/ vision_describe（本地 VLM）三件并列 MCP 工具、无程序化优先级，大模型自主选择何时/用何工具观察。

04 Vision SoM 通道图（MCP 化）

关键设计：agent（LLM）是唯一判断者；本地 VLM 只是它的「眼睛/外层 tool」。SoM marks 跨步状态自持于 tool 内 som://last_result（α 决策，已落地：omni_core/tools/vision_tool.py 持有 _last_marks，VisionRuntime 改为无状态的 tap_mark(mark)；能力实现在同层 L1 的 vision_runtime.py，已迁出 omni_core/local/），内核零感知。agent 可用 som_last_result 工具重读。

图 N4 · Vision SoM 通道（工具插件态）。本地 VLM 仅作为视觉外层 tool 返回结构化区域，最终点击决策仍由 Brain 做出（tap_by_mark 双路：结构化 ref → tap_by_id；视觉 center → 鼠标点击）；marks 状态自持于插件内 som://last_result。

05 自升级 Meta-loop

长期变强的闭环（护城河核心，框架外保留）。轨迹由 L2 钩子落盘，经 Quality Filter 后晋升为 Skill / 沉淀为 SFT 语料；权重级升级在 M5，且须经人工确认（策略 A）。

图 N5 · 自升级 Meta-loop（护城河）。Skill 与 Dataset 源自同一批轨迹；权重级升级在 M5，且必须经 Quality Filter 与人工确认（策略 A），避免「乱点 20 次最后成功」被学成策略。

06 通用多 agent 编排 + Escalation（LangGraph Send 扇出）

框架态（M10 已落地，multi-agent-redesign）：去分层——不再有固定的「manager 规划 + worker 执行」两层。主 agent（主模型）默认自己把任务做完；只有互不依赖、可并行的子任务群，主 agent 才调 dispatch 元工具产出计划，编排层（omni_core/orchestration/graph.py，main / sub / finalize 节点）用 LangGraph Send 扇出子 agent（执行模型）并发执行，结果经 add reducer 聚合回灌主 agent。子 agent 干不动时靠可量化升级条件把现场交回主 agent（escalate）。

图 N6 · 通用多 agent 编排 + Escalation（M10 框架态）。主 agent 默认自己做完；调 dispatch 才 Send 扇出子 agent 并发执行，结果 add reducer 聚合回灌；干不动才 escalate 回主 agent。架构决策（2026-09-17 评估）：保留图编排（Send 扇出含批次栅栏 / 预算分配 / 轮次上限），不迁移 SDK as_tool / handoff 原语——批次原子性与结构化控制是长任务刚需。

LangGraph 定位（2026-09-17 收束）：LangGraph 在本架构中只承担运行中编排——Send 并发扇出、轮次 / 预算控制、update_state 软注入。持久化一律交给领域层（WorldModel 落盘 + skill 沉淀，见 §08），不引入 SqliteSaver 等持久化 checkpointer。graph state 只记控制簿记（plan / results / round / budget），零领域数据。

07 上下文管理分层模型（大模型质量压缩 vs worker 硬滑窗）

两层架构下，大模型与 worker 的上下文目标不同，管理策略必须分开：worker 是「存活裁剪」（硬滑窗防溢出），大模型是「质量压缩」（handoff 前瞻摘要 + token 占比主触发）。1M 窗口 ≠ 不压。压缩 / 滑窗策略由框架 lifecycle 钩子执行，owner 变框架。

图 N7 · 上下文管理分层模型（框架态）。worker 硬滑窗存活裁剪（绿），大模型 token 占比主触发 + handoff 质量压缩（紫）。二者策略不可混用；压缩/滑窗由框架 lifecycle 钩子执行。
为何「1M 窗口 ≠ 不压」：Claude 官方称大窗口下的退化叫 "context rot"；Chroma 2025 实测 200K 窗口自 50K token 起性能明显退化（lost-in-the-middle）。Codex / Claude / Hermes 全都在压——大窗口只给跑大任务的余量。OmniAgent 大模型走 OpenAI 兼容接口，模型可任意替换，真实窗口因所选模型而异，token 占比必须相对其真实窗口算。

08 超长任务持久化与检查点模型

OmniAgent 会跑小时级甚至跨天常驻任务（长任务少干预诉求），不能靠 /clear 续命。解法：把大部分状态根本不进窗口——无状态大模型 + 持久世界模型落盘 + 子目标检查点续跑。压缩写回世界模型以规避 JPEG 效应。这是「长任务少干预」的护城河支点。

图 N8 · 超长任务持久化与检查点模型（护城河）。子目标分解给 worker 干净本地 ctx，边界写 checkpoint 到持久 world-model；大模型无状态、每次只收快照+当前子目标，崩溃可续。
机制作用是否进 LLM 窗口
无状态大模型（每次调用重建上下文）只收「world-model 快照 + 当前子目标 / 升级原因」，不累积历史 → 几乎不触发压缩极小（仅当前轮）
持久外部记忆（world-model 落盘）目标 / 约束 / 已学事实 / 进度，每次调用重注入；压缩怎么压都不丢仅摘要指针注入
子目标检查点（checkpoint 落盘）子目标边界把 world-model + 当前子目标写盘；崩溃 / 重启从检查点续不进窗口
行业对齐：Codex 警告「多次压缩导致模型准确度下降」（JPEG 效应）；Zylos 2026 结论——长任务靠「压缩 + 结构化外部记忆 + 子 agent 委派」三层，且压缩有损，外部记忆才是连续性真靠山。OmniAgent 两层架构骨架已朝此方向，world_model 持久化 + 检查点已落地（M4b.1）：`world_model.py` save/load(current.md) + checkpoint(JSON) + merge_progress(防 JPEG)；`_plan`/`_reflect` 无状态化（只组装 `world.summary()`）。框架态下该机制不变，仅压缩/checkpoint 触发点改由框架 lifecycle 钩子驱动。
架构决策（2026-09-17）：不引入持久化 checkpointer（SqliteSaver 等）。推理链：① LLM 上下文有限 → 长任务必然滑动（压缩 / 滑窗，见 §07），「恢复全量执行状态」本就不存在；② 崩溃恢复后模型重建认知靠的仍是 WorldModel 快照 + skill 沉淀，而非逐步执行轨迹；③ 通用 checkpointer 存全量 state 快照，体积大且大部分是模型吃不回的旧上下文——领域定制的 WorldModel（只存认知要点）粒度更对，且 skill 升级沉淀实现跨任务复用。LangGraph checkpointer 维持 MemorySaver 内存版，仅作软注入（update_state）通道使用，不承担持久化职责。HITL 需求为「运行中不中断」（软注入 + /stop），评估后不做 interrupt 审批暂停点。

09 全局目录与 Project / Task 模型

定义 agent 所有持久资产的落盘位置：用户全局 ~/.omniagent/（跨 project）。原 workspace / app 概念已从内核彻底删除（北极星红线），改为 project（路径 slug）+ 独立 task 两实体。与框架无关，纯资产落盘约定。

9.1 目录结构

~/.omniagent/                     # 用户全局（跨 project，~ = 用户主目录）
  config.yaml                     # 去明文 key + 端点；三通道(planner/executor/vision)由 Web 设置面板写入
  skills/                         # 通用 skill（跨 project 共享，含 Curator 升级产出）
  memory/                         # 知识层（K 系列）记忆子系统：跨会话长期记忆（非「全量加载」）
    MEMORY.md                     #   全局长期记忆（仅追加、可人工编辑）
    memory_summary.md             #   注入专用视图（截断 20000 字符、可随时再生）
    merged.json                   #   已合并 task_id 清单（幂等去重核心）
    rollouts/<task_id>.md         #   单任务蒸馏记忆，头部关联原始轨迹路径
    signals_aggregate.json        #   K2 信号聚合基线（假成功率 / 分歧率 / C₁·C₂ 分布）
    steady_state.json             #   K5 稳态判据与收敛状态
  projects/<path-slug>/           # project = 工作目录逻辑分组（id = 路径 slug），仅存会话历史 jsonl
  tasks/<task_id>/                # task 一等实体，独立平铺，含自身全部资产
    task.json                     #   元信息（objective / state / project_id? / runs）
    trajectory.jsonl              #   该 task 轨迹
    world_model.md                #   该 task 世界模型 / checkpoints
    collected.json                #   采集结果
    skills/                       #   该 task 私有 skill（可选）
  rules/
目录层级内容 / 用途
config.yaml全局真 API key（去仓库）、模型端点、local_model.auto_start、三通道（brain / runtime.executor / runtime.vision，各自独立 enable + base_url/model，由 Web 设置面板「通道」Tab 写入 ~/.omniagent/config.yaml）。框架态下三通道仍作为 model provider 接入 SDK。
skills/全局通用 skill 存全局（跨 project 共享）；task 私有 skill 存 tasks/<task_id>/skills/。recall 合并、task 优先。Curator 提炼的通用 skill（带 scope: global）落全局，实现「技能升级跨项目复利」。
memory/全局知识层（K 系列）记忆子系统：MEMORY.md 全局长期记忆（仅追加、可人工编辑）+ memory_summary.md 注入视图（可随时再生）+ rollouts/<task_id>.md 单任务蒸馏记忆 + merged.json 去重清单；另有 signals_aggregate.json（K2 信号基线）与 steady_state.json（K5 稳态）。不是「每会话全量加载」——注入走截断后的 summary 视图，且默认关闭、需显式开启。
projects/<path-slug>/全局project = 工作目录的 slug 分组，仅承载会话历史 jsonl；不装资产。
tasks/<task_id>/全局task 一等实体：自身含全部资产（trajectory / world_model / collected / skills）+ task.json 元信息。可关联一个 project_id（仅作 cwd 元数据，不影响落点）。

9.2 Project 与 Task 归属规则

  1. 指定工作目录 → project_id = slugify_path(绝对路径)，会话历史落 projects/<project_id>/；task 资产仍落 tasks/<task_id>/（资产与 project 解耦）。
  2. 未指定工作目录（GUI / 游戏等） → auto_project_id() 自动造 ~/OmniAgent/<date>-task-N，永远有 project 归属，避免 null 分支。
  3. task 资产跟 task 走：tasks/<task_id>/ 存全部重资产；project 仅作会话历史容器，不重复存。
  4. 前端历史 task list：平铺读 tasks/，按 state / 时间排序，不按 project 嵌套。

9.3 三通道解耦 + 统一 /chat

「运行模式三态」已演进为 三通道解耦：planner(brain) / executor(runtime.executor) / vision(runtime.vision) 三个通道各自独立 enable + base_url/model/api_key，Web 设置面板「通道」Tab 写入 ~/.omniagent/config.yaml，保存后即时生效。框架态下三通道作为 SDK 的 Model provider 接入（C3 模型无关）。

通道作用独立配置
planner（brain）规划 / 反思，看全局base_url / model / api_key，始终在线
executor（runtime.executor）子 agent 执行模型（dispatch 扇出时）enabled + base_url / model / api_key；关闭时由主模型兼任（executor_is_planner=True，统一入口不退化）
vision（runtime.vision）本地 VLM 视觉工具（vision-mcp 后端）enabled + model / base_url
红线不变：目录结构只是资产落盘位置的约定，不引入任何 app / 游戏 / 场景专属逻辑。内核路径统一由 runtime_paths.py（task_* / project_* / slugify_path / auto_project_id）提供，搜不到 app 作为分区键。北极星红线（内核零场景硬编码）延续。

10 前端设计（HITL 双通道 = C5）

单页 Shell + 三页 + 自研 Store。设计理念：Codex 风格——对话框下任务 + 实时进展流（SSE）+ 执行中可插话。前端已实现的 /stop 与插话队列，正是 §3.5 C5 的 HITL 双通道。通道归属（2026-09-17 评估收束）：软注入已走 LangGraph 原生 update_state（M8 落地：运行中往图状态追加纠偏消息，不打断当前 turn）；/stop 维持自研 ToolLoop.request_stop() 标志位（由 run_subtask_sdk 在块间轮询）；interrupt 审批暂停点评估后不做——HITL 需求为「运行中不中断」（软注入 + 硬停止已覆盖）。

10.2 自研 Store（React Context，零依赖）

全局 UI 状态集中在 TaskStoreProvider，通过 createContext 下发，组件用 useTaskStore() 消费。状态粒度：

  • 视图：view: "chat" | "skills" | "settings" + setView（单页切换，无路由跳转）。
  • 任务：tasks[] / projects[] / currentTaskId + refreshTasks()（调 taskApi.list() + projectApi.meta() 平铺）。
  • 运行：running / currentTaskId / maxSteps（步数上限）+ sendMessage()（统一走 runtimeApi.chat，首条自动建 task）。
  • 消息 & 流：messages[] / pushMessage / clearMessages；snapshot（RuntimeSnapshot）+ connectStream() / disconnectStream()（SSE）。
设计取舍：不引入 zustand/redux——状态规模小、且要零额外依赖；Context + useMemo 足够。SSE 连接挂在 store 上，保证切页不断流（Chat 切到 Settings 再切回，进展流不中断）。

10.4 交互范式（Codex 风格 + HITL 双通道 C5）

  1. 统一对话 / 任务：Chat 页主区即对话。发消息即 runtimeApi.chat()：首条消息后端自动建 task 落盘并回填 task_id；内部直接进统一入口 run_task——单链路，模型自主判断纯文本回答（方案 B 收尾）还是调工具执行，会话历史单路注入；需要并行时调 dispatch 扇出子 agent（M10 去分层）。不再做闲聊 probe 快判——追问等无工具消息也自然走 agent 链路，展示与上下文统一。
  2. 实时进展流：connectStream() 接 SSE，把后端状态机事件（OBSERVING/PLANNING/EXECUTING/VERIFYING）实时渲染为消息流。
  3. C5-A 硬停止：发 POST /api/runtime/stop 置位 ToolLoop.request_stop() 标志位（由 run_subtask_sdk 在块间轮询优雅退出），随后用户输入新指令 → 大模型重新执行。长任务中人工随时可强行接管。
  4. C5-B 软注入插话：流未结束时仍可向 messages 注入用户消息（经框架运行时消息注入队列），实现 human-in-the-loop 纠偏——循环不中断，下一步 agent 改路继续。优先级：人类注入 > L2 自治决策 > 框架默认策略。
  5. 两栏布局：左 Sidebar 平铺 task 列表 + 「新建会话」；右主区整页覆盖显示当前 view（chat/skills/settings），无路由跳转。
红线延续：前端不写任何场景 / app / 游戏专属逻辑或文案；所有领域数据来自后端配置与 API。UI 仅做通用 agent 控制台，能力暴露完全由后端 *Api 决定。

11.2 三实体一致率模型（K2）

「任务到底算不算成功」不是一个布尔值，而是三方口径的交叉：

实体是什么来源
A 系统判定run 结束的 successloop.run_task → result["success"]
B 模型自报本轮 assistant 结论文本会话末条 assistant 内容
C 真值交互段 C₁＝用户下一条消息裁决；自主段 C₂＝终态观测评审session jsonl / trajectory 终态观测
用途：抓假成功——A 说成功、C 说没有（例如用户回「不对，重做」）。 派生指标：假成功率 / 漏报率 / 分歧率 / 不可判占比，按交互·自主分模式统计，写入 tasks/<tid>/<run_id>.signal.json 并累加到 memory/signals_aggregate.json。 纯前向采集：只采集新任务，不回溯历史，无手动脚本，用户零操作。
