# 唱歌管线（清唱点歌）· 设计与实施 · 2026-11-02

> 状态：**已实施（MVP）**。清唱点歌：歌声转换声库 + 本地曲库 + 在线曲库 + IM 语音发送；
> 私聊与群内点歌双通道实测通过。
> 实施过程、逐次实测数字与踩坑复盘只保留在本地工作记录（不入仓）；
> 本文只保留可复用的判断、架构与结论，不含部署细节。
> 前置：`doc/plans/implemented/voice-2026-10-31.md` §8（语音工具明确"不能唱歌"）、
> §11.2（唱歌与 TTS 选型无关，单独走 RVC 管线）。

## 0. 结论

清唱 = 输出里不含伴奏，**不是"唱歌的简化版"，而是歌声合成（SVS）的原生形态**；加 BGM 是后期
多一步混音。前期最短路径是「**分离离线缓存 + 歌声转换（SVC）在线**」：点歌秒级到十几秒返回。
架构完全复用现有语音插件的「独立 venv 子进程 + capability」形态，内核零 import、零分支。

## 1. 三种范式（决定后面所有选型）

| 范式 | 输入 | 输出 | 需要源干声？ | 需要乐谱？ |
|---|---|---|---|---|
| **TTS**（现役 TTS 引擎） | 文本 | 说话 | 否 | 否（**无音高控制，唱不了**） |
| **SVC** 歌声转换 | 别人唱好的干声 + 音色参考 | 目标音色唱同一旋律 | **是** | 否 |
| **SVS** 歌声合成 | 歌词 + 旋律（MIDI 音符或 F0 轮廓）+ 音色参考 | 从零生成歌声 | **否** | **是** |

- SVC 保留原唱的旋律 / 节奏 / 咬字 / 情感，只换"谁在唱"——社区"AI 翻唱"全是这条。
- SVS 只生成人声，**天然就是清唱**；代价是必须有谱。
- 两条路要拿到角色音色，都靠"音色参考"或"训练声库"，与 TTS 的音色素材可以同源。

## 2. 调研结论：没有可直接抄的"虚拟主播唱歌模块"

2026-11 对三个主流开源虚拟主播项目做全量 tree 扫描（不是看 README 宣传）：

| 项目 | 唱歌代码 |
|---|---|
| `moeru-ai/airi`（5 万★级） | **无**（全路径扫 sing / karaoke / svc / rvc / vocal 零命中） |
| `Open-LLM-VTuber/Open-LLM-VTuber` | **无**（只有 TTS 说话适配） |
| `Ikaros-521/AI-Vtuber` | **无**（只有 TTS 说话适配；仓库里的 svc 目录是用户自塞样本） |

闭源标杆（Neuro-sama）的记录显示其程序组成含「演唱预录歌曲的软件」，并单独发过唱歌模型版本
——**说话声库与唱歌声库是两套，曲子是预生成的**。

**结论**：唱歌 = 一条独立管线 + 一个曲库，闭源标杆也是这么做的。这反而简化设计：
**不必追求实时流式唱歌**，离线预生成 + 缓存是业界常态。

### 3.2 RVC 的能力边界（主线引擎，源码 + 官方 FAQ 查实）

#### (1) 它是转换器，不是合成器

必须有**源干声**，输出严格跟随源的旋律 / 节奏 / 咬字，**源跑调它就跑调**。

- **做不了"填词唱"**——没有源干声就无从转换，那条路只能零样本 SVS。
- 点歌只能是**曲库模式**；点一首没预制的歌 = 现场跑分离（分钟级）。
- **不能改旋律 / 节奏 / 歌词**；**F0 编辑至今未实现**（changelog todolist 唯一未划掉的项）。
  修跑调只能在 RVC 之外做预处理。

#### (2) 音色 vs 音质的线性两难（官方 FAQ Q11）

> 底模与推理源音质高于训练集时可带高结果音质，代价是音色往底模/推理源靠（"**音色泄露**"）；
> `index_rate` 调到 1 理论上无泄露，但音质更倾向训练集；训练集音质低时调高还可能**降质**。

**最坏组合**：训练集 = 变声器产物、~1.7min、有底噪；推理源 = 商业歌曲干声（高音质）。
于是 `index_rate` 高 → 把训练集底噪与 artifacts 带进歌声；低 → 音色泄露成原唱。
**一个旋钮线性权衡，无两头都好的解。** 源码印证：检索混合就是
`npy * index_rate + (1 - index_rate) * feats`。

配套两条官方口径：
- **Q9**：训练集音质差底噪大，20~30 epoch 足够，调太高也**带不高**训练集音质
  → **训练修不了素材质量**。
- **Q10**：推荐 **10–50min**；5–10min 要求"精简 + 音色有特色"；1–2min「成功经验是其他人
  不可复现的」；<1min 没人成功过。**现有素材约 102s ≈ 1.7min，正落在不可复现档**。

#### (3) 歌声特有的物理限制（源码查实）

| 限制 | 证据 | 对唱歌的影响 |
|---|---|---|
| **HuBERT 输入固定 16kHz** | `infer/vc/pipeline.py` `self.sr = 16000` | 8kHz 以上的气声 / 齿音 / 呼吸细节在特征提取阶段就丢了；歌声比说话更依赖这些 |
| **F0 硬夹 50–1100Hz** | `pipeline.py` 夹取区间 | 1100Hz 略高于 C6 → **女高音超过 ~C6 被夹住** |
| **检索库 = 训练素材的 HuBERT 特征** | `docs/en/faiss_tips_en.md` | 素材没覆盖的音区无近邻可检索 → **纯说话素材训的库，高音区哑 / 破音** |
| **音量包络强制跟随源** | `pipeline.py` `change_rms(...)` | 输出动态是原唱的，不是目标音色自然的 |
| **FCPE 给静音帧插值出音高** | `pipeline.py` `f0[uv] = np.interp(...)` | 换气 / 停顿处可能出 artifact |
| **长音频分段推理** | `x_pad / x_query / x_center / x_max` | 有接缝风险；这几个参数也是 OOM 时的调节旋钮 |
| **F0 方法只剩 3 种** | `("pm","rmvpe","fcpe")` | harvest / dio / crepe 已被移除 |

**辟谣**：社区常说「RVC 把 F0 量化成 256 bin 所以有电音感」。量化确实存在（50–1100Hz 分 254 档），
**但它只进 encoder 的 conditioning embedding**；真正驱动输出音高的是**连续 f0** → NSF 正弦激励。
**所以"量化直接导致音高阶梯化"不成立**，电音感需另找原因，不要拿它当选型依据。

#### (4) 工程坑

- **依赖与现有 TTS venv 硬冲突** → 必须独立 venv（见 §7）。
- **`onnxruntime-gpu` 版本钉子**：DLL 不匹配会**原生崩进程、Python 捕获不到**。
  **但可避开**：RMVPE 的 `import onnxruntime` 是条件分支，走 `.pt` 即纯 PyTorch 路径。
- **路径敏感**：空格 / 括号 / 中文路径会炸 ffmpeg 与 filelist utf8
  → **缓存文件名必须用 `song_id` 哈希，不能用歌名**。
- **采样率锁定**：不能中途改采样率续训，v1(40k) / v2(48k) 一开始就要选对。
- **Windows 需 VC++ redist**。
- **推理模型 ≠ 训练 ckpt**：分享 / 推理用 `weights/` 下 **60+MB** 的 pth，不是 `logs/` 下
  几百 MB 的 G/D；拿错会报 f0 / tgt_sr 等 key 不存在。

#### (5) 好消息（避免只记坏账）

- **fairseq 已去掉**，改 `transformers` 的 HuBERT → RVC 过去最大的编译坑没了。
- **官方直接提供 cu128 依赖清单** → 新架构（sm_120）有现成路径，不用自己改 torch 钉子。
- **`faiss-cpu` 而非 gpu** → 检索不吃显存。
- **推理显存可调**（官方 Q8：4G 以下放弃，4G 还有救）：缩小 `x_pad/x_query/x_center/x_max`
  即可 → 8GB 卡有余地；"≈2.1GB"只是某配置下的值，**不是下限**。
- 2026-07 起：特征提取 / 训练 / 索引**可中途掐断续跑**、支持 FCPE、实时模式 CUDA Graph。

#### (6) 对选型的影响

**(2) + (3) 检索库那条叠加 → 瓶颈是素材，不是引擎。**
素材先过 **5–10min 硬下限**（说话也行），**歌声**素材往上加（补高音区），比在
RVC / 零样本 / Applio 之间纠结重要得多。

**(1) 决定 RVC 只能做曲库点歌。** 想要"群友给歌词就唱"必须上零样本 SVS——那 12–16GB 买的是
**能力**，不是音质，这么算它的账反而清楚了。

### 3.3 训练素材纪律

**结论：带 BGM 训练是致命的，引擎的"自带降噪"救不了。必须先分离成干声。**

#### 训练目标就是原始 wav 的频谱

`train/data_utils.py` 的 `get_audio()`：`load_wav_to_torch` → `spectrogram_torch`，
返回 `(spec, audio_norm)` 送生成器与判别器。**喂进去的伴奏，就是模型被要求重建的东西。**

#### `train/preprocess.py` 不含分离/降噪，只做四件事

| 步骤 | 实际作用 |
|---|---|
| "denoising" | **48Hz 五阶巴特沃斯高通**，只切超低频隆隆声 / DC。**对伴奏（100Hz–10kHz）完全无效** |
| 滤波实现 | 官方文档说的 `filtfilt` **已被注释掉**，改 `lfilter`（防零相位滤波的 pre-ringing） |
| 静音切片 | 阈值 −42dB；有 BGM 时 RMS 降不到 −42dB → **切不动** |
| 定长强切 | 每 3.7s 硬切（官方文档写 4s，以代码 3.7s 为准）→ **每片都带 BGM，且切在乐句中间** |
| 峰值归一化 | 线性缩放，**不改变人声/伴奏比例**；但缩放系数由伴奏峰值瞬态决定 → **各片段人声电平不一致** |

> **文档过时提醒**：官方 `training_tips_en.md` 写的 denoising 实现与 f0 方法和当前代码不符，
> 读它时以源码为准。

#### 带 BGM 的四条污染路径

1. **频谱目标**含伴奏 → 伴奏与音素内容不相关，模型把它的**平均频谱能量当成"音色"学进权重**
   → 输出常驻一层糊 / 底噪。
2. **HuBERT 特征**从含伴奏的音频提取 → 内容特征被污染。
3. **检索库 index** 就是这些被污染的特征 → **脏进权重，还脏进检索库，双重永久**。
4. **F0 提取**在多声部音频上抓错（旋律乐器 / 八度错）→ 音高条件错。

叠加 Q9「底模音质无法带高低音质训练集」→ **训练修不了，只能事前洗干净**。
**训练侧的纯净度要求高于推理侧**：进权重是永久的，推理源只影响那一首且 `index_rate` 可调。

#### 分离栈 RVC 已自带（协同好处）

`assets/pymss_weights/` 自带 BS-Roformer（SDR 12.97）、Mel-Roformer karaoke、去混响模型
→ **不用另接分离器**，避开 onnxruntime MDX 的原生崩进程风险；且**训练素材与曲库歌曲共用同一套分离栈**。

⚠️ **变声器音色的额外风险**：频谱本就不自然，分离模型对它的效果**必须实测**，不能假设与自然人声
同等。`dereverb` 要谨慎——过度处理会削掉气声。
**缓解手段是分离前置**：素材的**原始音源**如果拿得到，就在**变声器之前**分干声、再过变声器——
分离器永远面对自然人声；只有变声器产物是唯一入口时才后置分离，且必须先实测。

#### 多声源合并

manifest 格式 `speaker_name|speaker_id|repeat`，输出键 `ms%04d_s%03d_%s`。

- **同一角色的不同录音** → 直接混进同一训练目录当单说话人，**是好事**，补时长 + 音域覆盖；
  `repeat` 可过采样短素材。
- **不同角色 / 不同人** → 用多说话人 manifest，或分开训多个模型。
- ⚠️ **坑**：不同声源若来自**不同处理链（不同工具或不同设置）**，artifacts 不一致 →
  模型会平均它们 → **音色不稳定**。找新声源时尽量保持处理链一致。

#### 一个选错就白训的开关

官方 training tips：模型不考虑音高会更轻，**但不适合唱歌**。对应两套架构：
**带 NSF 音高激励的那个 ← 唱歌必须用**；无音高版本只能说话。
底模 v1(40k) / v2(48k)；**采样率一旦定了不能中途改**。

### 3.4 曲库筛子

模型训一次永久复用，但**每首新歌仍有成本**：下载 → 分离干声 → F0 提取 → 转换 → 缓存 → 发送，
其中**分离是分钟级、每首一次**，转换是秒级。分离结果缓存后永久复用 → **同一首歌第二次点是秒发**。

**"拉什么都能唱好"不成立**，曲库要过筛子：

| # | 门槛 | 依据 | 可否事前筛 |
|---|---|---|---|
| 1 | **音域匹配** | `f0_up_key` 只移 F0（`f0 *= pow(2, key/12)`），**音色仍在训练音区**；移太多哑/破，±12 半音不免费 | ✅ 按声库音域挑歌 |
| 2 | **别超 ~C6** | F0 硬夹 50–1100Hz | ✅ |
| 3 | **语言匹配** | HuBERT 内容特征 + 训练素材音素覆盖；中文素材唱日/英文歌咬字退化 | ✅ |
| 4 | **必须独唱** | 和声/对唱分离后是混合人声轨，F0 在重叠人声上严重出错，且所有人被转成同一音色 | ✅ |
| 5 | **别用"消音版/伴奏版"** | 多为相位相减 karaoke，把居中的人声削掉、留一堆混响，非合格 SVC 源；要从**原曲**提干声 | ✅ |
| 6 | **检索库覆盖** | index 来自训练素材，未覆盖的音区/音素无近邻 | ⚠️ 靠补素材 |
| 7 | **`index_rate` 两难** | 商业干声音质 > 训练集 → 音质与音色相似度只能选一头 | ❌ 每首都要调 |

**第 1/3/4/5 条可事前筛** → **曲库不是"拉一堆歌"，而是"按声库音域和语言挑歌"**。
这件事做好点歌成功率才高，否则群里点十首有六首翻车。

**拟人标准下的收敛**：产品验收线是"像是她在唱"而非精准翻唱，硬筛收敛为
**1 音域可移调覆盖 / 3 语言匹配 / 4 独唱** 三条；门槛 2/6/7 与咬字要求降级为质量项
（电音感、咬字糊可接受），门槛 5 保留（源质量差，分离必翻车）。副歌定位用能量峰值启发式 +
manifest 手工标记覆盖，不做语义级检测。

## 4. 三条可落地路线

### 路线 A：SVC + 预制曲库（前期主线）

```
歌曲 → 人声分离(干声) → F0 提取 → SVC(prompt=角色参考音频) → 角色清唱 → 缓存 → 发送
```

引擎取舍**定稿：直接走微调（RVC / Applio 系）**，理由是"微调进权重 > 每次喂参考音频"的音色范式
结论 + 可与现有 TTS 共存。两候选记录保留：

- **A1 零样本 SVC**：不训声库，prompt 直接用现有音色参考。输入契约极简
  （`prompt_wav + prompt_f0 + target_wav + target_f0`，加自动音域对齐/移调/半精度），
  **不需要歌词、不需要 MIDI**；输出 24kHz wav，可像 TTS worker 一样常驻加载、重复调用。
- **A2 微调（RVC / Applio / so-vits-svc-fork）**：与 TTS 同范式（训练进权重）。

**⚠️ 必须正面说的矛盾**：既有血泪教训是该音色属**分布外音频**，zero-shot 范式在这个音色上
翻过车（余弦 0.06–0.09），微调才救回来。A1 又是 zero-shot。歌声专用模型泛化基础更强，
但**能不能吃下这个变声器音色，必须实测，不能假设**。按已有范式结论，**大概率最终要走 A2**；
A1 的价值是"半天成本换一个可能省掉训练的机会"，外加它附带 SVS 能力。

**资源账**：A2 增量磁盘 ≈**6–8GB**（**必须独立 venv**，与 TTS venv 版本硬冲突，复用会搞坏
现有 TTS）、显存 ≈2.1GB 起 **可与现有 TTS 共存**；A1 增量 ≈12–16GB、显存 ≈4.3GB
**与 TTS 不能共存**。**磁盘差只有约 1.5–2 倍，不是数量级差**——选 A2 的主要理由是音色范式
与"不破坏现有语音体验"，**不再是省钱**。

**A2 的素材坑**：训唱歌声库，**纯说话素材不够**——说话素材里没有歌声的音高分布，高音区会哑/破音。
凑素材时**优先找该角色的歌声片段**，而不是更多说话片段。

### 路线 B：零样本 SVS → 任意歌词 × 固定旋律 = 群互动填词唱

```
歌词(群友给/模型写) + 旋律(预制 MIDI/F0 模板) + 角色参考 → 直接生成清唱
```

- **互动性最强的形态**：不是"点歌放成品"，而是"群友给词，角色当场唱"。
- 输入契约：`prompt_wav + prompt_metadata.json + target_metadata.json + phoneset`，
  `control=melody|score`，自动音域对齐 + 半精度。
- **代价：必须有谱，且自动转谱不可靠**。官方明确警告自动预处理的歌词/音符对齐不准，
  **强烈建议手工用 MIDI Editor 校正** → 不适合全自动实时。
- 落地取舍：预制一个**旋律模板库**（常见儿歌 / 热门副歌 MIDI，人工校一次），歌词按音节能填。
  前期 5–10 个模板足够玩，且模板可复用、质量可控。

### 路线 C：整曲生成 → 提取人声 → SVC（后期，带 BGM 时再上）

- 词+风格→整首歌；8GB 档配置可跑。
- **自带 REST API**（提交任务 + 轮询结果），无头集成友好，不必开 WebUI。
- 三个边界：
  1. **分轨只有 base 模型支持**，turbo / sft 都不支持；8GB 上要靠 offload，慢。
     "8GB 又快又能分轨"不成立。
  2. **`cover` 是风格/编曲翻唱，不是音色克隆**——想要角色音色仍然要接 SVC，别被名字骗了。
  3. `vocal2bgm` 正好是后期"清唱→加伴奏"的现成能力。
- 定位：**角色创作原创歌**的路线，不是前期清唱的最短路径。链路最长（生成→分离→转换→混音）。

## 5. 推荐架构（复用现有形态，零新红线）

沿用「独立 venv 子进程 + capability」，唱歌对大脑同样只暴露一个工具：

```
plugins/voice（现有 TTS 链路不动）
  capability  voice_sing(song_id, section?) -> wav bytes
              （MVP 只开曲库点歌；melody/lyrics 填词参数后置，先窄后宽）
  sing_worker.py   子进程（独立 venv）
  ~/.omniagent/models/sing/{prompts/, songs/, melodies/, cache/, material/}
  # songs/manifest：song_id ↔ 歌名 / 音域 / 语言 / 独唱标记 / 来源（曲库筛子靠它执行）
  # material/：离线投喂的原始文件（用户目录下、仓库外，永不进 git）

plugins/messaging
  msg_sing(...)    工具；描述里写清能力边界：只能唱曲库里的歌 / 按模板填词，
                   不能任意原唱、不能改旋律（与 msg_send_voice 的"不能唱歌"描述对称）

gateway/channels/<im>.py
  send_sing → 复用 send_voice 的 file URI / base64 兜底 / 失败降级文本

gateway/dispatch.py
  外部通道 tool_allowlist 加 msg_sing
```

- **内核零 import、零分支**不变；唱歌插件不注册旋律/乐谱编辑类工具（外部通道注入面不变）。
- **GPU 占用分引擎，别一刀切**：
  - **RVC 很轻**：模型 ~60MB `.pth` + 几十 MB `.index`，推理显存 ~2.1GB → 与 TTS 在 8GB 上
    **有可能共存**（需实测），不必严格互斥。
  - **零样本 SVS / 分离模型较重**：8GB 下建议与 TTS 互斥。
  - TTS 预热抑制分档：互斥引擎唱歌期间**必须**抑制（`transcribe()` 成功后会 prewarm，
    否则两个 worker 抢卡）；RVC 共存场景允许照常 prewarm，实测挤卡再收。
- **空闲回收**：唱歌比语音更低频，`sing_idle_sec` 可以比 `tts_idle_sec`(600s) 更短。
  杀进程仍是唯一能 100% 归还内存的手段。
- **缓存分层，不要只缓存成品**（关键设计）：
  - **L1 干声 + F0 + 伴奏轨**（每首歌分离一次，永久缓存）——分离是唯一分钟级重活，
    离线做掉就永久消失；伴奏轨顺手存着，后期加 BGM 直接用。
  - **L2 成品清唱**（热门曲目预生成）——点歌 = 查缓存 → 秒发。
  - 只缓存 L1 不缓存 L2 也能玩：点歌时当场跑转换（秒级），且支持"同一首歌换调"。
    曲库扩展成本因此低得多。
- **并发与限流**：
  - `msg_sing` 纳入现有群聊限流入队纪律，不另造一套；
  - **同 `song_id` in-flight 去重**：同一首歌转换进行中再点，直接回"在唱了"，不排队不重算
    （既有的出站同文去重只管已发出的消息，管不了进行中的任务）；
  - **异步补投形态**：`msg_sing` 立即返回"我练练"文案，合成进后台队列；完成后把语音补投进
    该会话（对齐 auto-chain / 补投机制的时序），补投文案带回指（1–2min 后话题可能已翻页）。
  - **失败同样补投**（获取失败 / 分离翻车 / 转换异常都要说一句话，不许静默吞掉）；
  - **MVP 曲库边界**：MVP 只对**本地投喂曲库**开放（全部预分离，无在线分钟级任务）；
    库外点歌直接拒（"这首我还不会唱"），在线获取是后续降级路径。
- **在线曲库（带 gate，排后）**：
  - 用途收窄为**曲库自动扩容**，不是主路径——MVP 先用手工投喂把链路打通；
  - 已知代价：无官方下载 API，走第三方接口（脆弱）；**搜索错配**（点 A 歌下到 live / 翻唱 /
    伴奏版——源错全错，宁可不唱）；在线源码率常见偏低，分离质量打折（拟人标准下可容忍）；
  - **公开仓滥用面**：下载适配器入仓 = 给所有读仓库的人一个"点歌下载器"。适配器独立成模块、
    默认关、接口地址走本地配置不入仓；提交前按红线过一遍。
  - 触发链路与本地曲库同一条（获取→分离→缓存 L1→转换），只是 L1 miss 时多一段分钟级获取，
    全程后台异步 + in-flight 去重。

## 6. 延迟预算

| 场景 | 延迟 | 可行性 |
|---|---|---|
| 点 **L2 已预生成** 的歌 | <1s（查缓存直发） | **完全可行** |
| 点 **L1 已预分离** 的歌，当场转换 | 约 5–15s | **可行** |
| 任意新歌，从原始混音全链现算（副歌 60s） | 约 30–60s | **可行，但必须异步** |
| 同上，整首 4min | 约 1.5–3min | 可行但不该在群里发整首 |
| 像说话一样 <3s 首包唱任意新歌 | — | **这个确实不行** |

- 转换不是瓶颈（社区实测：30s 干音数秒出结果；实时变声端到端 170ms）。
- **分离才是大头，且每首歌只需一次**（社区口径 4min 歌 1–2min；实测同量级或更好）。
- 零样本 SVS 的延迟**不能套用转换口径**：它是多步采样（flow-matching），比检索式单次前向重得多。
  选它是为了填词能力，**不是为了速度**。

**结论：不是硬件不行，是"哪一步放在线"的问题。** 分离离线化 + 转换在线，点歌就是秒级到十几秒。
而且群聊本来就是异步的——30–60s 后收到一条语音完全自然。只需要：
1. 工具描述里写清"唱歌要等几十秒"，**不要阻塞文本回复**（先回一句"我找找这首歌"）；
2. 长任务不要卡在 WS 线程里；
3. 同文去重按 `song_id` 而非文本。

## 7. 资源纪律

- **必须独立 venv**：与现有 TTS venv 的 torch / pydantic / gradio / transformers / fastapi 全线冲突
  → 复用会降级并**大概率搞坏现有 TTS**。冲突几乎全来自 WebUI 栈（headless 可不装），
  但 **torch 版本钉子绕不过**，独立 venv 省不掉。
- **分离与转换拆两阶段、两个 worker**：分离是分钟级重活、每首一次、可离线批量跑、**跑完即杀**；
  转换是秒级、需低延迟，可与 TTS 共存。若分离也常驻，要再加一份分离模型显存，共存结论就不成立。
- **显存分档**（8GB 级卡，实测/估算分开标）：
  | 组合 | 显存需求 | 结论 |
  |---|---|---|
  | TTS + 转换 | 3.7–5.1 GB | **可共存** |
  | TTS + 转换 + 分离同驻 | 4.7–7.1 GB | ⚠️ 边界→超，**共存失效，需拆阶段** |
  | TTS + 零样本 SVC | 5.9–7.3 GB | ❌ 必须 GPU 互斥 |
  | TTS + 零样本 SVS | 7.0–8.4 GB | ❌ 必须互斥 |
- **内存比显存更紧**：零样本多模型同驻 RSS 可达 20GB 级 → **headless + 只装 SVC 所需 + 裁掉 ASR
  是必须项，不是优化项**。转换只加载 HuBERT + 主模型，RSS 1–2GB 量级。
- **互斥的隐藏代价**：TTS 冷启动 12s。唱歌挤掉 TTS 后，唱完再说话要重等预热 → 唱歌期间
  **必须抑制** TTS 预热。
- **回收：杀进程是唯一能 100% 归还的手段**。同进程卸载回收不了内存（torch CPU 分配器 +
  glibc 碎片 + ONNX arena 不还系统；实测 WS 5148MB 只降到 4591MB）。走子进程的话，代价是
  **一次性冷启动**，不是常驻。
- **转发壳会不会杀不干净？不会**：venv 的 `python.exe` 是壳、真实解释器是它的子进程，
  壳退出时子进程一起被杀（launcher 用 Job Object + KILL_ON_JOB_CLOSE），
  现有 idle-kill 写法正确，**不需要额外 `taskkill /T`**。

## 8. 验收方法

- **多次采样取均值**（同配置三次合成底噪 p10 能差 30dB，单次采样会把运气当改进）。
- 指标三件套（按路线分指标）：
  - **说话人余弦**（与 TTS 验收同一把尺，可直接对比说话基线）——微调路线主判据；
  - **F0CORR / F0RMSE**——**SVS 路线的指标**；转换路线输出 F0 按构造跟随源，
    这组数只量 F0 提取链，量不出"唱功"；
  - **咬字 CER**（现有 STT 回验）——**先测原曲干声的 STT 作对照基线**，
    否则会把"唱歌导致 STT 变差"误判成"转换咬字差"；
  - 第三判据是**听感 artifacts**（电音 / 哑 / 破），只能人耳。
- **关卡 0（SVS 路线门前，go/no-go，半天）**：拿现有音色参考 + 一首歌干声跑零样本，
  听 + 量余弦。**余弦掉到 0.5 以下、或听感"不像本人" → 该路线作罢，不要调参硬救**。
- **关卡 1**：3 首歌 × 3 seed，确认稳定性（不是挑最好的一次）。
- **止损线**：关卡 1 两轮迭代（含补素材重训）后，余弦 / 听感仍不过线 → 歌唱特性整体搁置、
  只留调研结论，不再投入。
- **验收口径**：产品验收线 = 拟人标准（不破音 + 音色可辨 + 有唱歌起伏）；
  上述余弦 / CER 数字是诊断仪器，不是上线门槛。素材第一版用说话素材先训
  （选歌 + 移调兜底高音区），歌声素材之后补。
- **关卡 2**：接 IM 实发，确认时长 / 播放 / 风控。这条本身不是门槛——IM 只是运输通道，
  重点是唱歌链通不通。

## 9. 推进顺序

0. **素材工程**（硬下限管启动，歌声素材管上限）：**5–10min 处理链一致素材即可启动训练**
   （说话素材也行）；歌声片段是质量目标，不是启动门槛；**全部先分离成干声再训练**，
   能拿到原始音源就在**变声器之前**分；多声源合并**保持处理链一致**；记录素材的音域与语言
   （后面挑曲库的筛子）。
1. **环境验证**（独立 venv，不复用 TTS venv）：官方 cu128 依赖在新架构上能否装通；
   **必须选带音高的 NSF 架构**，选错白训；顺手量转换 RTF、峰值显存（TTS 常驻 / 不常驻两态）、
   分离显存与耗时。
2. **训声库 + 关卡 1**：3 首歌 × 3 seed 确认稳定性；按 §8 方法学测余弦 / CER / 听感；
   `index_rate` 按两难扫一遍，找音色与音质的可接受折中。
3. **搭 `sing_worker`（转换）+ `sep_worker`（分离，跑完即杀）** + 曲库（3–5 首副歌）
   + `msg_sing`（异步补投）→ **清唱上线**。
4. **曲库按筛子扩充**。
5. **互动填词唱**（路线 B）——此时才需要零样本 SVS，先过关卡 0。
6. **加 BGM**：分离出的伴奏轨对齐混音，或用整曲生成引擎的 vocal2bgm。

## 10. 已定决策

1. **产品形态 = 点歌名**：点一首歌名 → 生成 30–60s"像是她在唱"的清唱。
   **验收线 = 拟人标准，不是翻唱标准**：不破音 + 听得出是角色音色 + 有唱歌的起伏感 = 过；
   咬字糊一点 / 电音感一点可接受（AI 翻唱的普遍预期）。SVC 范式下旋律/节奏/咬字继承源干声，
   "像唱歌"由范式保证，失败模式收敛为破音（音域）、音色不像（index 两难）、分离底噪三类。
2. **异步补投**：工具立即返回（先回"我练练"），合成在后台跑，完成后补投语音；
   **失败也要补投说话**，不许静默。在线曲库作为库外获取的降级路径，带 gate 排后。
3. **素材方向**：留在**同源声源**——曾考虑真人清唱试点，因该声源没有说话素材、
   换声必然"唱歌一个音色、说话另一个音色"的音色割裂而放弃。
   素材总时长约 5min、单一来源、码率偏低（更高码率需登录，拟人线先不折腾）。
   ⚠️ 音轨形态（纯清唱 or 带 BGM）需确认：带 BGM 则 §3.3 的分离流程与"分离器对该音色的效果"
   实测重新适用。**素材来源信息只记本地，不进公开仓**。
   **语言门槛**：素材语言 ≠ 点歌语言时，唱歌（SVC）咬字退化可接受（内容主要来自源干声）；
   说话（TTS）退化明显——纯外语音源训 TTS 说中文必须实测，素材里混 1–2min 中文段有显著帮助。
4. **曲库范围**：MVP 硬筛 = 独唱 / 语言匹配 / 音域可移调覆盖。

## 11. 实施结果（脱敏）

**声库训练**：v2 48k + NSF、77 切片、300 epoch ≈53 分钟、batch 4，训练显存 ~5GB 与桌面共存。
**关卡 1 数值**：4 首 × 3 seed 说话人余弦 **0.913–0.950**，跨 seed ±0.003；epoch 定档 e200（0.941）。

**转换实测**：50s 副歌 **≈12s 全程**（特征 0.5s / F0 4.2s / 合成 2.8s），冷启动后同机复测 **7.2s**；
分离 **19–28s/首**。音乐域输出 vs 素材余弦 0.906–0.950。

**说话回转检验**：同一素材经声库回转后与 TTS 说话参考余弦 **0.438**（<0.5 线）；判别实验：
回转输出 vs 素材 **0.760**（模型确实在渲染该音色，渲染税 ≈0.17）→ 说明**说话链与唱歌链不同源**，
不构成否决项（主观听感终审定档可用）。**这条以后不必再当止损线**。

**接入**：`sing_worker`（子进程，协议同 TTS worker）、`voice_sing` 能力（懒启动 / 串行 / 空闲 300s
回收）、`msg_sing` 工具（曲库查找→转换→发送，库外 / 失败都有降级话术）、`send_sing`
（record 双路径 + `song:` 前缀去重）、dispatch allowlist。

**并发护栏**：`_SING_BUSY`（TTL 900s，`acq:<归一点歌话>` / `song:<曲库id>` 两把键）挡重复产能占用；
`_INFLIGHT` 按归一歌名做 single-flight；`_SEP_LOCK` 让分钟级分离全局单飞；
起线程失败释放占位、不留死锁；`InFlightError` 只记日志静默退（那一句已由占位者口播过）。

**真缺陷与修法（值得记）**：同一份插件文件在一个进程里被装载两次 → **两个引擎 worker 单例**。
根因：插件 loader **按文件路径**装载（`_omni_plugin_voice`），而跨模块调用方按**包名**
`from plugins.voice import plugin` 取用 ⇒ 同一文件 exec 两遍、两个 module 对象、两份
`_SING_WORKER`。代价：显存/内存双份、`_lock` 的"全进程只有一路 GPU 唱歌"不变式失效、
在线链路白付一次冷启动。
**修法（不留双路径）**：新增 `plugins/voice/sing_runtime.py`，把**跨模块共享状态**整体搬过去
——worker 类 + 唯一实例、声库/解释器/仓库根路径、超时与 idle 常量、配置读取的唯一实现。
该模块**只按包名 import**，永远不经 loader ⇒ 全进程只有一份；依赖方向单向
`plugin.py → sing_runtime`（反向会把二次装载引回来）。护栏用例断言三处引用指向同一实例。

**在线曲库链路**：搜索 → 匿名凭证 → 直链下载 → 分离 → 切副歌 + 定 key → 入库。
全链实测 **54s / 79s / 115s / 156s**（下载是主变量，话术按最坏 2min 说）；
`sing_online` 为**用户级配置**、下载适配器留在用户目录（**公开仓零改动**，守住滥用面红线）。
- **筛选口径**：时长窗不拿搜索元数据判（拿不到 ≠ 0 秒，会把整首误杀），而是**下载完 ffprobe 实测**；
  超窗换下一个候选（最多 2 个），测不了则标 `screened` 不判死。语言与独唱没有检测器就写
  `unverified`，不假填。
- **入库标题必须清洗**：平台 SEO 长标题会作为话术字段被整句念出 = 刷屏。
  优先取书名号里的歌名，否则剥标签 + 首标点截断，兜底用点歌话；原标题存 `raw_title` 兼作别名。
- **磁盘**：每入库一首 ≈150MB（干声 stem + 分离出的伴奏轨，为后期 BGM 复用）；原始下载文件
  注册后即删。

**收尾**：曲库 9 首（在线入库 5 + 手工投喂 4），stems 1.6GB、outputs 34 个成品 148MB；
全量 908 用例 rc=0。

**操作纪律**：改 `plugins/**` 的**代码**必须重启网关进程才生效；改用户目录下的配置或曲库源
适配器**不用**重启（每次调用都重读）。

## 12. 开放项

1. **整首 stem 转换病理性慢**（4 分钟歌 >30min 不出、GPU 100%；50s 副歌正常）——
   怀疑大形状下 CUDA graph 反复捕获，待查；MVP 只转副歌不受影响。
2. **跨措辞重复获取**：不同说法在 ~80–150s 窗口内仍可能各下一遍（`_SING_BUSY` /
   `_INFLIGHT` 都按归一点歌话做键，跨措辞不合并）。
3. **护栏键是进程内内存态**：若 web 面板后端也能触发唱歌，两边互不可见——同歌并发要收就得
   落盘或用文件锁。
4. **L2 成品缓存**未做。
5. **`send_sing` 与 `send_voice` 合并**未做（刻意先分开，验收后再收）。
6. **库内点歌同步转换 7–8s 会阻塞下一条群消息**（dispatch 单条串行）——MVP 可接受，
   要解就得库内路径也走异步补投。
7. **在线点歌日志重复**：可用性探测与获取各加载一次曲库源，纯重复日志，不重复建连接。
