## 1. 问题陈述

**这不是容量问题,是表现问题。**

- 记忆层落盘很轻(`brain.db` 百 KB 量级、日记一天一篇),注入面也都有硬上限——磁盘增长不构成
  压力。因此本方案**不做**"存不下就删"的清理,淘汰只发生在**注入面**(移出常驻,不删文件)。
- 真正的问题是 **prompt 上下文里"记忆的表现"**,三个互相独立的失败:
  ① 接不住旧事(该召回时 0 条);② 每轮复读同一条(高频词垄断);③ 问到很久以前的事答不上
  (窗口外不可见)。
- 判据不看条数,看**信噪比**:注入的每一条是否与当前话题有关、是否带来新信息。

## 2. 现状诊断

### 2.1 注入预算:容量远没到瓶颈

一次典型 run 的各段注入量(字符,量级):

| 注入段 | 量级 | ≈token |
|---|---|---|
| L3 画像 `user_profile.md`(`_PROFILE_TRUNCATE=20000`) | ~0.8k | ~0.5k |
| L2 场景导航(任务块 + 7 篇日记窗口) | ~0.6k | ~0.4k |
| L1 原子记忆(`top_k=8`,有命中时) | 0.3–0.5k | 0.2–0.35k |
| **合计** | **1.5–2.5k** | **≈1–1.7k** |

结论:上下文占用不到 5%。**"数据变多会挤爆 prompt"不成立**,问题在注入了什么。

### 2.2 召回:只会复读高频词

40 条查询样本的召回条数分布:

| 召回条数 | 条数 |
|---|---|
| 0 | 4 |
| 1–2 | 2 |
| 3–5 | 14 |
| 6–8(满额) | **20** |

- 满额召回的 top1 几乎总是同一条:某条含**高频专名**的规则条目反复命中(内容略)。
- 该召回的召不回:与库内词汇零重合的日常问句 → 0 条(实测 4/40)。

### 2.3 四处根因(都在代码里)

**根因 A：相关性是"候选集内相对排名归一"**

```695:695:omni_core/memory_brain.py
rel = 1.0 - 0.5 * (i / max(n_rows - 1, 1))
```

命中任一高频词即进 15 条候选，**第 1 名恒 1.0、末位 0.50**，`inject_floor 0.30` 形同虚设。
实测某高频专名 query 的第 5 条,bm25 弱近 2 倍仍拿 0.50 → 注入。

**根因 B：纯 FTS5 词面匹配，无同义扩展**

一个词都不重合就 0 条。原仓库 standalone 默认也是 `embedding.provider="none"`（纯 BM25），
所以"没上向量"不算移植偏差；**但原仓库单路用的是绝对分**（见 §3）。

**根因 C：远期断档**

- 日记导航只露最近 `_DIARY_NAV_WINDOW=7` 篇（`omni_core/local/scene_executor.py:63,665`），
  第 8 天起不进 prompt；`read_scene` 能按名取，但导航不列 → 模型不知道它存在。
- 私聊/web 会话是**整条 jsonl 全量转 messages**（`backend/api/routers/helpers.py:471`，
  `chat_runtime.py:219,266`），只在 token 超阈值时压缩（`sdk_bridge.py:101` `_compress_history`，
  `retain_ratio 0.5`）。旧对话压缩后磨灭，且**没有任何检索入口**。
- 群聊已有 8 条窗口 + `msg_group_history`，但该工具走 OneBot `get_group_msg_history`，
  只能拉最近 N 条，跨天/跨周拿不到。

**根因 D：L2 导航只给文件名,模型无法判断该读哪篇**

`omni_core/local/loop/instructions.py:165-172` 的 M-1 策略是"零摘要、零热度",而原仓库注入的是
`Path + **热度** + Summary`(`MemoryCore/src/core/scene/scene-navigation.ts:113-115`)。后果:
`diary-<日期>.md` 这类文件名零信息量,模型看不出哪篇与当前话题相关 → 不会调 `read_scene`,
导航退化成"知道存在但用不上"。**这比"7 篇窗口截断"更早发生**:第 8 天的事还没轮到被截,前 7 天就已经没被读过。

### 2.4 与原仓库逐项核查(2026-11-02)

| 项 | 结论 | 依据 |
|---|---|---|
| L1 相关性 | **可对齐,但收益有限** | `simple` 分词器在位;真实 MATCH 下 bm25 = -1.64~-1.06 → `rel = -bm25/(1-bm25)` = 0.62~0.52。绝对分落点集中在 0.5–0.6,`threshold 0.3` 几乎挡不住任何命中(原仓库同样)。**对齐的价值是"不再把弱命中抬成 1.0"**,不是加严门槛;真正控量的是 k + 去冗余 |
| L1 条数 | **机制一致,仅参数不同** | 两边都是"检索→排序→截断 k→注入";原仓库 `maxResults=5` 拼在 user 前缀,我们 `top_k=8` 拼在起始 user 消息 |
| L2 注入形态 | **实质区别(关键)** | 原仓库每条三行(`Path`/`热度`/`Summary`);我们只有文件名。见根因 D |
| L2 条数上限 | 接近 | 原仓库 `maxScenes=15`;我们 `max_entries=20`(实配 5–11 条) |
| 写入去重候选 | **效果不一致,当前≈0** | 33 条 active 实测:`content[:12]` 短语候选 **0/33**;全文近邻 **9/33**。即去重/合并/矛盾判定从未触发 |
| 遗忘(decay/降级) | **原仓库没有,本仓库自创** | 原仓库只有 `retentionDays` 硬删(默认关)+ L2 `maxScenes`;本仓库有 salience 衰减与 dormant/archive 状态机(默认关) |

## 3. 与原仓库对照：哪些是移植偏差

| 机制 | 原仓库 | 本仓库 | 判定 |
|---|---|---|---|
| L1 进 prompt 的形态 | **自动注入已下线**，改为工具按需，`tdai_memory_search`+`tdai_conversation_search` 每轮合计 ≤3 次（理由：破坏 prompt cache） | 每轮自动注入 8 条 → **决定对齐：全局下线，改模型自取（P1/方案 C）** | **方向性偏离 → 已决策对齐** |
| 相关性分 | 单路绝对分 `rel/(1+rel)`（`MemoryCore/src/core/store/tokenize.ts:172`）；原生 BM25 时 `score >= threshold` 过滤、失败 rethrow | 自创候选集线性归一；失败静默返空 | **实现偏差**（实测绝对分落点 0.5–0.6，见 §2.4） |
| 向量召回 | standalone 默认 `embedding=none`；配 embedding 时 BM25∥向量 RRF(k=60) | 无 | 与默认一致，不算偏差 |
| L2 注入形态 | 每条 `Path` + `**热度**` + `Summary`（`scene-navigation.ts:113-115`），正文按需 `read_file` | **只有文件名**（M-1），零摘要零热度 | **实质区别**（见根因 D） |
| 去重候选 | FTS/向量近邻 top5 + 批量一次 LLM 判 store/update/merge/skip（`l1-dedup.ts`） | `content[:12]` 精确短语 + 每轮最多 8 次判定 | **实质降级**（实测候选 0/33） |
| 衰减/遗忘 | **完全没有** decay/dormant/archive/access_count；只有 retentionDays 硬删（默认关） | 自创 salience 衰减 + dormant/archive 阈值（默认关） | **自创，非移植**；决定删除 |
| 注入预算 | 条数 5；`maxCharsPerMemory`/`maxTotalRecallChars` 默认 0（不限）；`scoreThreshold 0.3` | 条数 8，无字符预算 | 接近 |
| 注入位置 | L3 常驻 system；L2 只给索引；L1/L0 只给工具 | L3 + L2 索引 + L1 每轮注入 | 见上 |

结论：**不换方案，也不整包接入原项目**（它是单会话语义，缺 peer / 群聊多人概念；
接入要引入 Node 服务栈）。要做的是把被改掉的三处改回去，并补上 L0 检索。

## 4. 设计原则

1. **窗口 + 检索，缺一不可**
   - 窗口管指代（"这/那个/刚才"）——必须给最近原文；
   - 检索管远期（"上周说的事"）——窗口外一律靠工具查，不回填全量。
2. **淘汰 = 移出常驻，不是删除**
   - 常驻层：画像 + 行为规则 + 压缩后的叙事锚（硬上限，靠压缩维持）；
   - 检索层：L1 原子记忆、关系卡、场景块正文（按需）；
   - 冷层：旧日记、老 episode、冷关系卡、完整场景块（**不进 prompt，可检索**）。
3. **相关性用绝对分,不用候选集内排名**
   - 排名分只适合融合(RRF 的用途),不适合做阈值门控;
   - 阈值门控必须有跨查询可比的绝对分。
   - **但别指望它单独救场**:实测 bm25 量级下绝对分落点集中在 0.5–0.6,门槛仍不区分好坏;
     控量靠 k 与去冗余(§2.4)。
4. **记忆是全局的,检索结果永不自动注入(2026-11-02 用户定,方案 C)**
   - 记忆系统一套,不按通道/场景做注入特例;通道只注入**消息上下文**(场合自述、
     群窗口、来源标注)与 **L2/L3 索引**(结构设定);
   - L1/L0 的**检索结果**一律由模型经工具自取(`memory_recall` / `conversation_search`,
     每轮合计 ≤3 次),返回进上下文一次,不重复;
   - 通道没有"群聊版注入",也没有"私聊版注入"——被 @ 或被回复时上下文本来就在,
     更早的靠工具查,这正是检索该有的形态。
5. **不改记忆的写入语义**（本轮不动 flush/四态判定），只改召回与注入；写入侧改进单列 P4。
6. **分层术语(2026-11-02 定)**:L0 分两支——**L0-消息**(`s_*.jsonl`,会话原文)与
   **L0-叙事**(`diary-<日期>.md`,日粒度原料;由 LLM 产出但**不进注入面**、不参与 L2 容量,
   只可检索与按需读)。L2 只放抽象层(主题块 + 日记摘要索引 + 月记);"淘汰"的含义是不进 L2。

### P6 · L2 导航对齐原仓库(渲染 + 分族配额;改 `instructions.py` + `scene_executor.py` + `memory_brain.py`)

**分层口径(2026-11-02 定)**:`s_*.jsonl` = **L0-消息**;日记 = **L0-叙事**(日粒度原料,
全量保留、可检索、不注入);**L2 只放抽象层**(主题块 + 日记摘要索引 + 月记)。
L2 索引严格对齐原仓库 `Path + 热度 + Summary` 三行(`scene-navigation.ts:113-115`)。

1. **渲染**:每条三行——`- <文件名>` + `  热度 N(主题块)/ 日期(日记、月记) · 更新 YYYY-MM-DD`
   + `  <summary>`。主题块 summary 是维护 agent 写的(30–60 字),日记 summary 是首句(第 4 条)。
2. **分族配额**(2026-11-02 用户定):主题块 **≤10**(heat 降序)/ 日记**最近 7 篇**
   (日期倒序;heat 恒 0 不参与排序,渲染成日期)/ 月记最近 2 篇。总条数 ≤19
   (超出原仓库 `maxScenes=15`:我们的 summary 更短——120 字对 30–40 词,且 19 条
   是"索引条数",主题块实际只有个位数;**字符预算 ≈1.9k 才是硬约束**)。
   字符预算 ≈ 10×120 + 7×60 + 2×100 ≈ **1.8k**。
3. **"近期摘要"不再单独提炼**:直接用 7 篇日记的 META.summary 当索引条目——零新产物、
   零额外 LLM 调用,且可按日期精确回溯("上周三"→定位那篇)。"合并成一条周叙事"留作
   可选增强,需要跨天连续感时再作为普通 L2 主题块增量添加。
4. **必修 bug + 放宽**:`write_diary_block` 的 `summary = text[:60]` 硬截会断句
   (实测有"…后来不知怎么冒出")——改为"取首个句号/问号/叹号结尾的句子,≤60 字";
   日记 prompt(`memory_brain.py:1002`)的"≤450 字"放宽为"**≤900 字**"
   (归 L0 后不再受注入预算约束;`read_scene` 的单块读取上限不变)。
5. 删 `_recent_diary_note`(`gateway/channels/napcat.py`):其职责由导航里的日记 summary
   覆盖,避免同一段话在同一次 run 里注入两遍。

验收:注入字符 ≤1.5k;被点名 run 中"主动 `read_scene` 读日记"次数 0 → >0(轨迹可观测);
新生成日记的 summary 不再有断句;旧日记的断句 summary 由下次月记/读全文兜底,不回填。

### P0 · 打分校准 + 去冗余（改 `omni_core/memory_brain.py`）

改动：

1. `search_brain` 的相关性改绝对分（照抄原仓库公式），**不保留 `rank_norm` 开关、
   不保留候选集线性归一的旧代码**（2026-11-02 定:旧实现本身有问题,不留兼容分支;

   def bm25_rank_to_score(rank: float) -> float:
       """FTS5 bm25 越小越相关（负值）→ 绝对相关性 [0,1)。"""
       rel = -float(rank) if rank < 0 else 0.0
       return rel / (1.0 + rel)

   基线对照用已有日志(judgments / 40 条样本在 §2.2 的分布),不需要运行期开关。

### P1 · L1 自动注入**全局**下线，改模型自取（方案 C，2026-11-02 用户拍板）

**架构原则（先于实现）**：记忆是整套系统共用的，**不按通道/场景做注入特例**。
通道只注入**消息上下文**（场合自述、群窗口、来源标注）；记忆的**检索结果永不自动注入**——
L1/L0 一律由模型经工具自取。被 @ 或被回复时上下文本来就在（8 条窗口），模型也有工具能查
更早的记录，这才是正确方式。L3 画像与 L2 索引仍常驻 system（结构设定，与原仓库一致）；
关系卡摘要随场合自述带出，属于"当前对话对象索引"，不是检索结果。

改动：

1. **删 run 起始的 `<relevant-memories>` 自动注入**（`inject_text_brain` 的调用点；
   函数保留，`memory_recall` 工具继续走 `search_brain`）。**私聊与群聊同规则，不设群聊特例**。
2. `top_k` 8 → **5**（对齐原仓库 `maxResults`，工具返回同样受此约束）。
3. system 增《记忆使用规则》（中文化照抄原仓库 `MEMORY_TOOLS_GUIDE`）：
   必查场景（被问过往事件 / 人物关系 / 主人相关信息）、每轮 `memory_recall` +
   `conversation_search` **合计 ≤3 次**。
4. 观测：`memory_recall.jsonl` 记 `{ts, project, source(T0/T1/private), 调用次数, hits,
   top1_id, 零查标记}`——"该查而没查"可从 run 轨迹对出来。

验收：抽检 20 条被点名 run 的"该查而查"比例；零查 run 的回答质量不塌（人工评）；
`memory_injected` 层列表不再含 L1。

### P2 · L0 检索：写入即入表 + `conversation_search` 工具（对齐原仓库 `l0_conversations`）

原计划（独立 `l0_index.db` + mtime 扫描）**作废**——对齐后发现原仓库是
**"写入时同步插一行到主库"**（`l0_conversations` 表与 L1 同库，`memory-store.ts:606-618`），
`conversation_search` 直接查这张表（FTS5，可选向量 + RRF）。

改动：

1. **`brain.db` 新增 `l0_messages` 表 + `l0_fts`**（对齐 `l0_conversations` 字段）：
   `record_id / chat_id / kind(chat|task) / role / speaker(uid) / text / recorded_at / timestamp`；
   `kind` 区分群消息与任务输入（两者同为 `role=user`，防检索串味）。
2. **写入即入表**：`ProjectStore.append_message` 尾部同步插一行（失败静默，不阻断主流程）；

5. 配额：`conversation_search` + `msg_group_history` **每轮合计 ≤3 次**；工具自述写清
   "问到具体的人/时间/约定/旧事时用"。

验收:能查到 7 天前的具体约定(构造用例);单次调用 ≤300ms(本地 FTS);

## 8. 风险

1. **绝对分会换掉 top-k 的人**:实测绝对分集中在 0.5–0.6、几乎都过门槛,所以注入**条数不会减少**,
   变的是**同分段的排序**(强命中更靠前、弱命中后移)。缓解:改前先落一份 40 条样本的基线
   (`memory_recall.jsonl` 或 §2.2 分布),改后直接对比;不设运行期开关。
2. **P1 全局下线自动注入后,模型可能"该查而不查"**(私聊与群聊同规则,不设回退特例)。缓解:
   system 的《记忆使用规则》列明必查场景(被问过往/人物关系/主人信息)+ 每轮 ≤3 次配额;
   `memory_recall.jsonl` 记录调用率与零查标记,人工抽检 20 条评质量。
3. **P2 首次上线**要回填全部会话 jsonl(一次性成本,量级 MB);之后写入即入表,无批量扫描。
4. **P3 窗口化**可能让长程任务(同一 task 多轮)丢上下文。缓解:窗口按"轮"而非"任务"计,
   任务卡(`_TASK_CARD_KEEP`)保留在窗口内。
5. **P6 恢复摘要会挤占 system 字符**:分族配额 ≈ 1.4k,是现状的 2.3 倍。缓解:主题块
   summary ≤120 字、日记 ≤60 字 + 总条数 15 双上限;`memory_injected` 轨迹里记 chars,超预算告警。
6. **P6 取消周叙事后,"跨天连续感"靠模型自己串 7 条按天的 summary**。若实测
   "这周过得怎么样"类问题串不起来,再增量添加一条周叙事主题块——不是回退,是补强。
7. **P6 放宽日记字数(450→900)后**:`read_scene` 单块读取上限不变,超长日记会被截断
   只读前段;月记的原料也变长。缓解:900 字是软约束(prompt),超长的一天优先写细节而非流水。
