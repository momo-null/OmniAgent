## 0. 一句话

清唱 = 输出里不含伴奏，**不是"唱歌的简化版"，而是歌声合成（SVS）的原生形态**；
加 BGM 反而是后期多一步混音。前期最短路径是「**分离离线缓存 + 歌声转换（SVC）在线**」，
群里点歌秒级到十几秒返回（§5.1 有延迟预算），架构完全复用现有 voice 插件的
「独立 venv 子进程 + capability」形态，零新红线。

## 1. 先分清三件事（决定后面所有选型）

| 范式 | 输入 | 输出 | 需要源干声？ | 需要乐谱？ |
|---|---|---|---|---|
| **TTS**（现役 GPT-SoVITS） | 文本 | 说话 | 否 | 否（**无音高控制，唱不了**） |
| **SVC** 歌声转换 | 别人唱好的干声 + 音色参考 | 目标音色唱同一旋律 | **是** | 否 |
| **SVS** 歌声合成 | 歌词 + 旋律（MIDI 音符 或 F0 轮廓）+ 音色参考 | 从零生成歌声 | **否** | **是** |

- SVC 保留原唱的旋律/节奏/咬字/情感，只换"谁在唱"——B 站"AI 翻唱"全是这条。
- SVS 只生成人声，**天然就是清唱**；代价是必须有谱。
- 两条路要拿到角色音色，都靠"音色参考"或"训练声库"，与 GS 的音色素材可以同源。

### 3.1 RVC 的局限（2026-11-02 源码 + 官方 FAQ 查实）

仓库：`RVC-Project/Retrieval-based-Voice-Conversion-WebUI`，39,000★、MIT、未归档，
last push **2026-08-04**，589 open issues，changelog 停在 2026-07-23 → **活着，但非高频迭代**。

#### (1) 能力边界：它是转换器，不是合成器

必须有**源干声**，输出严格跟随源的旋律 / 节奏 / 咬字，**源跑调它就跑调**。

- **做不了路线 B（填词唱）**——没有源干声就无从转换。那条路只能 SoulX SVS。
- 点歌只能是**曲库模式**；点一首没预制的歌 = 现场跑分离（分钟级，见 §5.1）。
- **不能改旋律 / 节奏 / 歌词**；**F0 编辑至今未实现**——changelog 的 todolist 里
  唯一没被划掉的项就是「F0 编辑」。修跑调只能在 RVC 之外做预处理。

#### (2) 音色 vs 音质的线性两难（官方 FAQ Q11，最命中本项目）

> 如果底模和推理源的音质高于训练集的音质，他们可以带高推理结果的音质，但代价可能是
> 音色往底模 / 推理源的音色靠，这种现象叫做"**音色泄露**"。
> index rate 调到 1，则理论上不存在推理源的音色泄露问题，但**音质更倾向于训练集**。
> 如果训练集音质比推理源低，则 index rate 调高可能**降低音质**。

**本项目正好是最坏组合**：训练集 = 变声器产物、~102s、有底噪（voice plan §9）；
推理源 = 商业歌曲干声（高音质）。于是 `index_rate` 高 → 把训练集底噪与变声器 artifacts
带进歌声；低 → 音色泄露成原唱。**一个旋钮线性权衡，无两头都好的解。**

源码印证：`infer/vc/pipeline.py` 的检索混合就是
`npy * index_rate + (1 - index_rate) * feats`。

配套两条官方口径：
- **Q9**：「训练集音质差底噪大，20~30 epoch 足够了，调太高，
  **底模音质无法带高你的低音质训练集**」→ **训练修不了素材质量**。
- **Q10**：推荐 **10–50min**；5–10min 要求"精简 + 音色有特色"；
  1–2min「成功经验是**其他人不可复现的**」；<1min 没人成功过。
  **现有 102s ≈ 1.7min，正落在不可复现档** → voice plan §13 待办 2 是硬前置，不是可选优化。

#### (3) 歌声特有的物理限制（源码查实）

| 限制 | 证据 | 对唱歌的影响 |
|---|---|---|
| **HuBERT 输入固定 16kHz** | `infer/vc/pipeline.py:54` `self.sr = 16000` | 8kHz 以上的气声 / 齿音 / 呼吸细节在特征提取阶段就丢了；歌声比说话更依赖这些 |
| **F0 硬夹 50–1100Hz** | `pipeline.py:74-75` | 1100Hz 略高于 C6(1046.5Hz) → **女高音超过 ~C6 被夹住** |
| **检索库 = 训练素材的 HuBERT 特征** | `docs/en/faiss_tips_en.md`：`3_feature256` → `big_npy [N,256]` | 素材没覆盖的音区无近邻可检索 → **纯说话素材训的库，高音区哑 / 破音** |
| **音量包络强制跟随源** | `pipeline.py:23` `change_rms(...)` | 输出动态是原唱的，不是目标音色自然的 |
| **FCPE 给静音帧插值出音高** | `pipeline.py:126-127` `f0[uv] = np.interp(...)` | 换气 / 停顿处可能出 artifact |
| **长音频分段推理** | `x_pad / x_query / x_center / x_max` | 有接缝风险；这几个参数也是 OOM 时的调节旋钮（Q8） |
| **F0 方法只剩 3 种** | `pipeline.py:71` `("pm","rmvpe","fcpe")` | harvest / dio / crepe 已被移除（changelog：被 RMVPE 取代） |

**⚠️ 辟谣（差点写错，查证后推翻）**：社区常说「RVC 把 F0 量化成 256 bin 所以有电音感」。
量化确实存在（`train/dataset/extract_f0.py:118` `np.rint`，50–1100Hz 分 254 档），
**但它只进 encoder 的 conditioning embedding**（`infer/module/models.py:40`
`emb_pitch = nn.Embedding(256, hidden_channels)`）。
真正驱动输出音高的是**连续 f0**：
`SynthesizerTrnMs256NSFsid.infer(..., nsff0, ...)` → `self.dec(z * x_mask, nsff0, ...)`
→ NSF 正弦激励（`models.py:309` `_f02sine`）。
`pipeline.py:139` `return f0_coarse, f0bak` 也印证：coarse 与连续值分别送两条路。
**所以"量化直接导致音高阶梯化"不成立**，电音感需另找原因，不要拿它当选型依据。

#### (4) 工程坑

- **依赖与 GS venv 硬冲突** → 必须独立 venv，详见 §5.2 冲突表。
- **`onnxruntime-gpu>=1.19.2,<1.20`**：正是 voice plan §11.3 记录的
  「DLL 不匹配 → 原生崩进程、Python 捕获不到」高危项。
  **但可避开**：`infer/rmvpe.py:513` 的 `import onnxruntime` 是条件分支，
  走 `.pt` 即纯 PyTorch 路径（changelog 20230813 明确 RMVPE 支持 pytorch/onnx/DirectML）。
- **路径敏感**（FAQ Q1）：空格 / 括号 / 中文路径炸 ffmpeg 与 filelist utf8
  → **缓存文件名必须用 `song_id` 哈希，不能用歌名**。
- **采样率锁定**（FAQ Q18）：不能中途改采样率续训，v1(40k) / v2(48k) 一开始就要选对。
- **Windows 需 VC++ redist**（FAQ Q16，`llvmlite.dll`）。
- **推理模型 ≠ 训练 ckpt**（FAQ Q4）：分享 / 推理用 `weights/` 下 **60+MB** 的 pth，
  不是 `logs/` 下几百 MB 的 G/D；拿错会报 f0 / tgt_sr 等 key 不存在。

#### (5) 好消息（避免只记坏账）

- **fairseq 已去掉**，改 `from transformers import AutoFeatureExtractor, HubertModel`
  （`infer/hubert.py` 实测）→ RVC 过去最大的编译坑没了。
- **官方直接提供 `requirments_cu128_py312.txt`** → sm_120 有现成路径，不用自己改 torch 钉子。
- **`faiss-cpu` 而非 gpu** → 检索不吃显存。
- **推理显存可调**（FAQ Q8：「4G 以下显存可以直接放弃，4G 显存显卡还有救」，
  缩小 `x_pad/x_query/x_center/x_max` 即可）→ 8GB 卡有余地；
  §5.2 引的 ≈2.1GB 只是某配置下的值，**不是下限**。
- 2026-07-18 起：特征提取 / 训练 / 索引**可中途掐断续跑**、支持 FCPE、
  实时模式 CUDA Graph（4090D 上延时最高加速 4.7 倍）。

#### (6) 对选型的影响

**(2) + (3) 检索库那条叠加 → 瓶颈是素材，不是引擎。**
素材先过 **5–10min 硬下限**（说话也行，§9 step 0 分层口径），**歌声**素材往上加（高音区质量），
比在 RVC / SoulX / Applio 之间纠结重要得多。

**(1) 决定 RVC 只能做曲库点歌。** 想要"群友给歌词就唱"必须 SoulX——
那 12–16GB 买的是**能力**，不是音质，这么算它的账反而清楚了。

### 3.2 训练素材：带背景音会怎样（2026-11-02 源码查实）

**结论：带 BGM 训练是致命的，且 RVC 的"自带降噪"救不了。必须先分离成干声。**

#### 训练目标就是原始 wav 的频谱

`train/data_utils.py:99-139` `get_audio()`：
`load_wav_to_torch(filename)` → `spectrogram_torch(audio_norm, ...)` → 返回 `(spec, audio_norm)`，
再与 `phone / pitch / pitchf / dv` 一起送生成器与判别器（`get_audio_text_pair` 返回六元组）。
**喂进去的伴奏，就是模型被要求重建的东西。**

#### `train/preprocess.py` 不含分离/降噪，只做四件事

| 步骤 | 代码 | 实际作用 |
|---|---|---|
| "denoising" | `preprocess.py:49` `signal.butter(N=5, Wn=48, btype="high", fs=sr)` | **48Hz 五阶巴特沃斯高通**，只切超低频隆隆声 / DC。**对伴奏（100Hz–10kHz）完全无效** |
| 滤波实现 | `preprocess.py:91-93` | 官方文档说的 `filtfilt` **已被注释掉**，改 `lfilter`；注释原因：`# zero phased digital filter cause pre-ringing noise` |
| 静音切片 | `Slicer(threshold=-42dB, min_length=1500, min_interval=400, hop_size=15, max_sil_kept=500)` | 有 BGM 时 RMS 降不到 −42dB → **切不动** |
| 定长强切 | `per=3.7, overlap=0.3` → 步进 3.4s | 兜底：每 3.7s 硬切，**每片都带 BGM，且切在乐句中间**（官方文档写 4s，以代码 3.7s 为准） |
| 峰值归一化 | `max=0.9, alpha=0.75`：`tmp/tmp_max*0.675 + 0.25*tmp` | **线性缩放，不改变人声/伴奏比例**（前一版写"伴奏占比更高"是错的，作废）。真实影响：缩放系数由**伴奏峰值瞬态**决定 → **各片段人声绝对电平不一致**，训练集响度不齐 |

> **文档过时提醒**：`docs/en/training_tips_en.md` 仍写 "denoising: smoothed by scipy's filtfilt"
> 与 "f0 用 parselmouth 或 pyworld"，**均与当前代码不符**（现为 lfilter + 48Hz 高通；f0 为 rmvpe/fcpe/pm）。
> 该文件只有 en/jp/fr/kr/pt/tr 版本，**没有 cn 版**。读它时以源码为准。

#### 带 BGM 的四条污染路径

1. **频谱目标**含伴奏 → 伴奏与音素内容不相关，拟合不出来，模型把它的**平均频谱能量
   当成"音色的一部分"学进权重** → 输出常驻一层糊 / 底噪。
   （机制由源码确定；**具体听感是社区共识 + 推断，本机未实测**）
2. **HuBERT 特征**从含伴奏的 `1_16k_wavs` 提取 → 内容特征被污染。
3. **检索库 index** 就是这些被污染的 `3_feature256` → **脏进权重，还脏进检索库，双重永久**。
4. **F0 提取**在多声部音频上抓错（旋律乐器 / 八度错）→ 音高条件错。

叠加 FAQ Q9「**底模音质无法带高你的低音质训练集**」→ **训练修不了，只能事前洗干净。**
**训练侧的纯净度要求高于推理侧**：进权重是永久的，推理源只影响那一首且 `index_rate` 可调。

#### 分离栈 RVC 已自带（协同好处）

`assets/pymss_weights/` 实测文件列表：
- `model_bs_roformer_ep_317_sdr_12.9755.yaml` ← **BS-Roformer，SDR 12.97**
- `model_bs_roformer_ep_368_sdr_12.9628.yaml`
- `config_mel_band_roformer_karaoke.yaml`
- `dereverb_mel_band_roformer_anvuew.yaml` ← **去混响**

**正是 §6 推荐的 PyTorch 系分离** → 不用另接 `audio-separator`，
**避开 onnxruntime MDX 的原生崩进程风险**；且**训练素材与曲库歌曲共用同一套分离栈**。

⚠️ **本项目额外风险**：音色是**变声器产物**，频谱本就不自然，
分离模型对它的效果**必须实测**，不能假设与自然人声同等。
`dereverb` 一步要谨慎——voice plan §9 教训之一是过度处理会削掉气声。
**缓解手段是分离前置（2026-11-03 补）**：素材的**原始音源**如果拿得到，
就在**变声器之前**对原始音源分干声、再过变声器——分离器永远面对自然人声
（SDR 12.97 的口径就是在这上面测的），上面这条风险直接消失，
变声器输出天然就是训练用干声。只有变声器产物是唯一入口（拿不到原始音源）时
才对它后置分离，且必须先实测。

#### 多声源怎么合并（`tools/multispeaker.py`，现已原生支持）

manifest 格式 `speaker_name|speaker_id|repeat`，输出键 `ms%04d_s%03d_%s`
（对应 `preprocess.py:203-217` 对 `ms` 前缀文件的特殊处理）。

- **同一角色的不同录音** → 直接混进同一训练目录当单说话人，**是好事**，补时长 + 音域覆盖；
  `repeat` 字段可过采样短素材。
- **不同角色 / 不同人** → 用多说话人 manifest（推理选 `speaker_id`），或分开训多个模型。
- ⚠️ **本项目的坑**：不同声源若来自**不同变声器工具或不同设置**，artifacts 不一致 →
  模型会平均它们 → **音色不稳定**。找新声源时尽量保持处理链一致。

#### 一个选错就白训的开关

官方 `training_tips_en.md` step1 原文：
> If the model doesn't consider pitch, the model will be lighter, **but not suitable for singing**.

对应 `infer/module/models.py` 两套架构：
- **`SynthesizerTrnMs256NSFsid`（带 NSF 音高激励）← 唱歌必须用这个**
- `SynthesizerTrnMs256NSFsid_nono`（无音高，更轻，只能说话）

底模 `f0G40k.pth` / `f0D40k.pth`（v1 40k）或 v2 48k；
**采样率一旦定了不能中途改**（FAQ Q18）。

### 3.3 曲库筛选：训好之后"拉歌就能唱"的七个门槛

**模型训一次永久复用——这点成立。** 但每首新歌仍有成本：

```
下载 → 分离干声 → F0 提取 → 转换 → 缓存 → QQ record
       └ 分钟级，每首一次 ┘   └ 秒级 ┘
```

分离结果缓存后永久复用（= §5 架构的 L1）→ **同一首歌第二次点是秒发**。

**曲库来源（2026-11-03 评审定）**：MVP 只允许**主人离线投喂**——自己下载原曲丢进
`~/.omniagent/models/sing/material/`，由管线分离入库；agent 不做在线下载/搜索，
合规面与下载依赖都不开。

**但"拉什么都能唱好"不成立，曲库要过筛子：**

| # | 门槛 | 依据 | 可否事前筛 |
|---|---|---|---|
| 1 | **音域匹配** | `f0_up_key` 是 `f0 *= pow(2, key/12)`（`pipeline.py:130`）——**只移 F0，音色仍在训练音区**；移太多哑/破，±12 半音不免费 | ✅ 按声库音域挑歌 |
| 2 | **别超 ~C6** | F0 硬夹 50–1100Hz（`pipeline.py:74-75`） | ✅ |
| 3 | **语言匹配** | HuBERT 内容特征 + 训练素材音素覆盖；中文素材唱日/英文歌咬字退化 | ✅ |
| 4 | **必须独唱** | 和声/对唱分离后是混合人声轨，F0 在重叠人声上严重出错，且所有人被转成同一音色 | ✅ |
| 5 | **别用网上"消音版/伴奏版"** | 多为 L−R 相位相减 karaoke，**把居中的人声一起削掉、留一堆混响**，非合格 SVC 源；要从**原曲**提干声 | ✅ |
| 6 | **检索库覆盖** | index 来自训练素材，未覆盖的音区/音素无近邻 | ⚠️ 靠补素材 |
| 7 | **`index_rate` 两难** | 商业干声音质 > 训练集 → 音质与音色相似度只能选一头（FAQ Q11） | ❌ 每首都要调 |

**第 1/3/4/5 条可事前筛** → **曲库不是"拉一堆歌"，而是"按声库音域和语言挑歌"。**
这件事做好了点歌成功率才高，否则群里点十首有六首翻车。

**拟人标准下的收敛（2026-11-03 拍板）**：产品验收线是"像是她在唱"而非精准翻唱（§10.1），
硬筛收敛为 **1 音域可移调覆盖 / 3 中文 / 4 独唱** 三条；门槛 2/6/7 与咬字要求降级为质量项
（电音感、咬字糊可接受），门槛 5 保留（源质量差，分离必翻车）。副歌定位用能量峰值启发式 +
manifest 手工标记覆盖（`chorus_start/chorus_end`），不做语义级检测。

#### 对资源账的修正（§5.2 共存结论要加条件）

§5.2 的"GS + RVC 显存 3.7–5.1GB 可共存"**只算了转换**（HuBERT + net_g）。
**若分离也在同一 worker 常驻，要再加 BS-Roformer 显存**（估 1–2GB，**未实测**），
共存结论不一定成立。

**建议分离与转换拆成两阶段**：分离是分钟级重活、每首一次、可离线批量跑；
转换是秒级、需低延迟。**分离 worker 跑完即杀，不与转换同驻**——
正好复用现有 idle-kill 形态（§5.2 已验证 terminate 能连带杀子进程）。

## 4. 三条可落地路线

### 路线 A：SVC + 预制曲库（前期主线）

```
歌曲 → 人声分离(干声) → F0 提取 → SVC(prompt=角色参考音频) → 角色清唱 → 缓存 → QQ record
```

引擎取舍**定稿：路线 A 直接走 A2/RVC，不再用实测二选一**（2026-11-03 评审：理由 = voice plan §11.2
音色范式结论 + 可与 GS 共存；SoulX 零样本实测整体移到路线 B 门前，见 §8 关卡 0 / §9 step 5）。
两候选记录保留：

- **A1 零样本（SoulX-Singer-SVC）**：不训声库，prompt 直接用 GS 的 `voices/*.wav`。
  实测输入契约极简（`cli/inference_svc.py`）：`prompt_wav + prompt_f0.npy + target_wav + target_f0.npy`，
  加 `--auto_shift`（自动音域对齐）`--pitch_shift` `--fp16`，**不需要歌词、不需要 MIDI**。
  输出 24kHz wav。`model.infer(...)` 是干净的 Python API，可像 `tts_worker.py` 一样常驻加载、重复调用。
- **A2 微调（RVC / Applio / so-vits-svc-fork）**：与 GS 同范式（训练进权重），符合 §11.2 已验证的结论。

**⚠️ 这里有一个必须正面说的矛盾**：§9/§11.2 的血泪教训是「该音色是变声器产物、属分布外音频，
zero-shot 范式在这个音色上翻过车（CosyVoice2 余弦 0.06–0.09），微调才救回来」。
A1 又是 zero-shot。SoulX 是歌声专用模型、42000h 训练量，泛化基础远强于 CosyVoice2，
但**能不能吃下这个变声器音色，必须实测，不能假设**。
按已有范式结论，**大概率最终要走 A2**；A1 的价值是"半天成本换一个可能省掉训练的机会"，
外加它附带 SVS 能力（路线 B），这是 RVC 给不了的。

**资源账（见 §5.2，2026-11-02 二次修正）**：A2 增量磁盘 ≈**6–8GB**（**必须独立 venv**，
与 GS venv 的 torch/pydantic/gradio 版本硬冲突，复用会搞坏现有 TTS）、
显存 ≈2.1GB 起 **可与现有 TTS 共存**（官方 FAQ Q8：可靠缩小分段参数降显存）；
A1 增量 ≈12–16GB、显存 ≈4.3GB **与 GS 不能共存**，且内存需裁 ASR 才塞得进 11GB free。
**磁盘差只有约 1.5–2 倍，不是数量级差**——所以选 A2 的主要理由是音色范式（§11.2）
与"不破坏现有语音体验"，**不再是省钱**。A1 只在确定要做路线 B 时才值得付互斥的代价。

**A2 的素材坑（提前说）**：RVC 训唱歌声库，**纯说话素材不够**。
说话素材里没有歌声的音高分布，训出来的模型在高音区会哑/破音
（社区共识："音高跨度大、超过目标音色舒适区的部分会变哑或破音"）。
§13 待办 2 本来就要把素材凑到 5–10min——**凑的时候优先找该角色的歌声片段**，而不是更多说话片段。

### 路线 B：零样本 SVS → 任意歌词 × 固定旋律 = 群互动填词唱

```
歌词(群友给/模型写) + 旋律(预制 MIDI/F0 模板) + 角色参考 → 直接生成清唱
```

- **互动性最强的形态**：不是"点歌放成品"，而是"群友给词，角色当场唱"。
- 输入契约（实测 `cli/inference.py`）：`prompt_wav + prompt_metadata.json + target_metadata.json + phoneset`，
  `control=melody|score`，`--auto_shift --fp16`。
- **代价：必须有谱，且自动转谱不可靠**。官方明确警告：自动预处理的歌词/音符对齐不准，
  **强烈建议手工用 MIDI Editor 校正** → 不适合全自动实时。
- 落地取舍：预制一个**旋律模板库**（生日歌 / 小星星 / 两只老虎 / 热门副歌 MIDI，人工校一次），
  歌词由模型按音节能填。前期 5–10 个模板足够玩，且模板可复用、质量可控。

### 路线 C：ACE-Step 1.5 原创整曲 → 提取人声 → SVC（后期，带 BGM 时再上）

- 词+风格→整首歌；8GB 档配置 = `2B turbo` DiT + `acestep-5Hz-lm-0.6B`（官方 GPU 分档表）。
- **自带 REST API**（`:8001`，`POST /release_task` → `POST /query_result` 轮询），无头集成友好，
  不必开 Gradio。
- 三个必须知道的边界（实测 README Model Zoo + INFERENCE.md）：
  1. **`extract`（分轨）只有 `base` 模型支持，`turbo`/`sft` 都不支持**。2B base 是 50 步 + CFG，
     8GB 上要靠 offload，慢。想要"8GB 又快又能分轨"是不成立的。
  2. **`cover` 是风格/编曲翻唱，不是音色克隆**（原文："changing style/timbre"，示例是
     `caption="orchestral symphonic arrangement"`）。想要角色音色仍然要接 SVC，别被名字骗了。
  3. `vocal2bgm` 正好是后期"清唱→加伴奏"的现成能力。
- 定位：**角色创作原创歌**的路线，不是前期清唱的最短路径。链路最长（生成→分离→转换→混音），
  四个环节都掉质量。

## 5. 推荐架构（复用现有形态，零新红线）

沿用 §10 的「独立 venv 子进程 + capability」，唱歌对大脑同样只暴露一个工具：

```
plugins/voice（现有 TTS 链路不动）
  capability  voice_sing(song_id, section?) -> wav bytes
              （MVP 只开曲库点歌；melody/lyrics 填词参数等 §9 step 5 落地再加，先窄后宽）
  sing_worker.py   子进程（SoulX 独立 conda env / RVC 独立 venv）
  ~/.omniagent/models/sing/{prompts/, songs/, melodies/, cache/, material/}
  # songs/manifest：song_id ↔ 歌名 / 音域 / 语言 / 独唱标记 / 来源（§3.3 七门槛靠它执行）
  # material/：主人离线投喂的原始文件（在 .omniagent 下、仓库外，永不进 git）

plugins/messaging
  msg_sing(...)    工具；描述里写清能力边界：只能唱曲库里的歌 / 按模板填词，
                   不能任意原唱、不能改旋律（与 msg_send_voice 的"不能唱歌"描述对称）

gateway/channels/napcat.py
  ReplyChannel.send_sing → 复用 send_voice 的 .wav file URI / base64 兜底 / 失败降级文本

gateway/dispatch.py:387
  外部通道 tool_allowlist 加 msg_sing（2026-11-03 核对：现为 8 个 = 5 个 msg_* +
  memory_recall/read_scene/conversation_search；加 msg_sing 后 9 个）
```

- **内核零 import、零分支**不变；唱歌插件不注册旋律/乐谱编辑类工具（外部通道注入面不变）。
- **GPU 占用分引擎，别一刀切**（2026-11-02 修正，见 §5.1）：
  - **RVC 很轻**：模型 ~60MB `.pth` + 几十 MB `.index`，推理显存 ~2.1GB（社区 4090 压测口径）。
    **GS + RVC 在 8GB 上有可能共存**（需实测），不必严格互斥。
  - **SoulX / 分离模型较重**：flow-matching 推理 + Roformer 分离叠加，8GB 下建议与 GS 互斥。
  - TTS 预热抑制分档（2026-11-03 评审修）：互斥引擎（SoulX / 分离）唱歌期间**必须**抑制
    （`transcribe()` 成功后会 prewarm，见 `plugins/voice/plugin.py:134`）；
    RVC 共存场景 3.7–5.1GB < 6.3GB，允许照常 prewarm，实测挤卡再收。
- **空闲回收**：唱歌比语音更低频，`sing_idle_sec` 可以比 `tts_idle_sec`(600s) 更短。
  杀进程仍是唯一能 100% 归还内存的手段（§10 已实测）。
- **缓存分层，不要只缓存成品**（关键设计）：
  - **L1 干声 + F0 + 伴奏轨**（每首歌分离一次，永久缓存）——分离是唯一分钟级重活，
    离线做掉就永久消失；伴奏轨顺手存着，后期加 BGM 直接用。
  - **L2 成品清唱**（热门曲目预生成）——点歌 = 查缓存 → 秒发。
  - 只缓存 L1 不缓存 L2 也能玩：点歌时当场跑 SVC（秒级），且支持"同一首歌换调/换音色"。
    曲库扩展成本因此低得多。
- **并发与限流（2026-11-03 评审补）**：
  - `msg_sing` 纳入现有群聊限流入队纪律，不另造一套；
  - **同 `song_id` in-flight 去重**：同一首歌转换进行中再点，直接回"在唱了"，不排队不重算
    （`_is_dup_send` 只管已发出的消息，管不了进行中的任务）；
  - **异步补投形态（2026-11-03 拍板）**：`msg_sing` 立即返回"我练练"文案，合成进后台队列；
    完成后走 run 级 auto-chain / 补投机制把语音发进该群（接线时对齐 barge-in queue 的
    block_id 后缀时序），补投文案带回指（"刚才点的《青花瓷》"）——1–2min 后话题可能已翻页。
    **失败同样补投**（下载失败 / 分离翻车 / 转换异常都要说一句话，不许静默吞掉）。
  - **MVP 曲库边界**：MVP 只对**本地投喂曲库**开放（全部预分离，在线分钟级任务不存在）；
    "库外点歌 → 在线获取 → 后台异步全链"是 step 4 的降级路径（带 gate，见下），
    MVP 阶段库外点歌直接拒（"这首我还不会唱"）。
- **在线曲库（2026-11-03 拍板：做，但 step 4 + gate）**：
  - 用途收窄为**曲库自动扩容**（库外点歌的降级路径），不是主路径——MVP 先用手工投喂把链路打通；
  - 已知代价，接之前心里有数：无官方下载 API，走第三方接口（脆弱、说挂就挂）；
    **搜索错配**（点《青花瓷》下到 live / 翻唱 / 伴奏版——SVC 源错全错，宁可不唱）；
    在线源常见 128k 码率，分离质量打折（拟人标准下可容忍）；
  - **公开仓滥用面**：下载适配器入仓 = 给所有读仓库的人一个"点歌下载器"。
    适配器独立成模块、默认关、接口地址走本地配置不入仓；提交前按红线过一遍。
  - 触发链路与本地曲库同一条（获取→分离→缓存 L1→转换），只是 L1 miss 时多一段分钟级获取，
    全程后台异步 + in-flight 去重。

## 5.1 延迟预算：实时点歌到底可不可行（2026-11-02 修正）

**初稿这里写错了**——原文"任意歌当场唱在 8GB 单卡上不现实（分钟级延迟）"把
「全链在线」和「点歌」混为一谈，且用 SoulX 的 flow-matching 步数去估所有引擎的延迟。
按引擎拆开重算：

| 场景 | 延迟 | 可行性 |
|---|---|---|
| 点 **L2 已预生成** 的歌 | <1s（查缓存直发） | **完全可行** |
| 点 **L1 已预分离** 的歌，当场 RVC 转换 | 约 5–15s（估算） | **可行** |
| 任意新歌，从原始混音全链现算（副歌 60s） | 约 30–60s（估算） | **可行，但必须异步** |
| 同上，整首 4min | 约 1.5–3min（估算） | 可行但不该在群里发整首 |
| 像说话一样 <3s 首包唱任意新歌 | — | **这个确实不行** |

**数据来源与边界**（实测 / 估算分开标）：

- 实测口径（社区，消费级 N 卡）：**RVC 离线推理 30 秒干音通常数秒内出结果**；
  3060 上 10 秒音频数秒出结果；**实时变声端到端 170ms（ASIO 90ms）**。
  → RVC 能做到流式麦克风变声，说明单帧计算极轻，**转换不是瓶颈**。
- 实测口径（社区，RTX 3060）：**人声分离一首 4 分钟歌约 1–2 分钟**。
  → 5060 估 40–90s；只切副歌 60s 则估 15–25s。**分离才是大头，且每首歌只需一次。**
- **5060 本机实测（2026-11-03 step 1 smoke，fp32 整段）**：HuBERT 0.0063 / RMVPE 0.031 /
  net_g 0.013，三组件合计 RTF ≈0.05 → 60s 副歌纯计算 ≈3s，**原外推的 5–15s 偏保守成立**；
  库外歌另计分离耗时。
- SoulX 的延迟**不能套用 RVC 口径**：它是 `n_steps=32, cfg=3` 的 flow-matching，
  比 RVC 的检索式单次前向重得多。选 SoulX 是为了 SVS 填词唱，**不是为了速度**。

**结论：不是硬件不行，是"哪一步放在线"的问题。** 分离离线化 + 转换在线，点歌就是秒级到十几秒。

**而且 QQ 群聊本来就是异步的**——群友不会盯着等 3 秒，30–60s 后收到一条语音在群里完全自然。
现有架构已经是异步的（dispatch 跑任务、模型调工具），这个延迟天然 fits，只需要：

1. `msg_sing` 工具描述里写清"唱歌要等几十秒"，**不要阻塞文本回复**（先回一句"我找找这首歌"）；
2. 长任务不要卡在 WS 线程里（对比 §8：入站转写是 1–3s 才敢同步做）；
3. 同文去重按 `song_id` 而非文本（见 §7）。

**唯一真正做不到的是"任意新歌、秒级首包"**，但那也不是点歌该有的产品形态。

### 运行时：显存能否共存

| 组合 | 显存需求 | vs 6.3GB free | 结论 |
|---|---|---|---|
| GS + RVC（**仅转换**） | 1.6–3 + 2.1 = **3.7–5.1 GB** | ✅ | **可共存** |
| GS + RVC（**转换 + PyMSS 分离同驻**） | 上式再 + BS-Roformer **估 1–2 GB** = **4.7–7.1 GB** | ⚠️ 边界→超 | **共存结论失效，需拆阶段** |
| GS + SoulX SVC | 1.6–3 + 4.3 = **5.9–7.3 GB** | ❌ 边界→超 | **必须 GPU 互斥** |
| GS + SoulX SVS | 1.6–3 + 5.4 = **7.0–8.4 GB** | ❌ | 必须互斥，SVS 单跑也近满卡 |

RVC ≈2.1GB 来自 4090 压测（Ubuntu / torch 2.1.0+cu121），SoulX 数来自第三方实测；
**均非本机 sm_120**，换 cu128 构建后可能变，§9 step 1 一并量。
**分离显存 1–2GB 是估算，未实测。**
**2026-11-03 smoke 实测**：RVC 三组件 fp32 整段推理峰值 **3.5GB**（GS 未运行态；fp16 + 分段推理
会显著更低）→ 上表"GS + RVC 仅转换"共存判断方向不变，正式数字待 sing_worker 接入后双态实测。

**→ 架构结论（见 §3.3）：分离与转换必须拆成两阶段、两个 worker。**
分离是分钟级重活、每首一次、可离线批量跑，**跑完即杀**；
转换是秒级、需低延迟，可与 GS 共存。这样上表第二行的风险就不存在。

**内存比显存更紧**：SoulX WebUI 多模型同驻 **≈20GB RSS**，本机只剩 **11.0GB free**
→ **headless + SVC-only + 裁 ASR 是必须项，不是优化项**。
RVC 只加载 hubert + net_g，估算 1–2GB RSS，加 GS 的 3.92GB 仍在余量内。

**互斥的隐藏代价**：GS 冷启动 12s。唱歌挤掉 GS 后，唱完再说话要重等 12s 预热。
所以 `plugins/voice/plugin.py:134`（`transcribe()` 成功后 prewarm）**唱歌期间必须抑制**，
否则两个 worker 抢卡。

### 运行完能否回收：能，100%，已在本仓验证

`plugins/voice/tts_worker.py` 的注释就是结论：
**同进程卸载回收不了内存**（torch CPU 分配器 + glibc 碎片 + ONNX arena 不还系统；
CosyVoice2 时代实测 WS **5148MB → 只降到 4591MB**）。**杀进程是唯一能 100% 归还的手段。**

唱歌直接复用 `_TtsWorker` 的 idle-kill：唱完 → 空闲 `sing_idle_sec` → 父进程杀 worker
→ 显存内存全回基线。唱歌比语音低频，`sing_idle_sec` 可比 `tts_idle_sec`(600s) **更短**
（建议 120–180s）。

**"生成一首歌之后会不会一直占着"不成立**——走子进程的话，代价是**一次性冷启动**，不是常驻。

**转发壳会不会导致杀不干净？已实测：不会。**
既然 venv `python.exe` 是壳、真实解释器是它的子进程，那 `_kill_locked` 里
`proc.terminate()` 打在壳上，理论上可能留下孤儿抱着 3.92GB 不放。
实测（另起 sleep 子进程复现，不碰生产 worker）：**壳退出时子进程一起被杀**
（venv launcher 用 Job Object + KILL_ON_JOB_CLOSE），`_kill_locked` 现有写法正确，
`sing_worker` 照抄即可，**不需要额外 `taskkill /T`**。

### 收益判断（2026-11-02 二次修正）

**只做前期清唱点歌（路线 A）→ 仍选 RVC，但理由换了**：
- ✅ 能与现有 TTS **共存**（显存 2.1GB 起，可调分段参数），不破坏语音体验、回收干净；
- ✅ 与 voice plan §11.2 的结论一致（微调进权重 > 每次喂参考音频），
  绕开 SoulX 零样本在这个变声器音色上大概率翻车的风险（§8 关卡 0）；
- ⚠️ **磁盘不再是优势**：独立 venv ≈6–8GB，与 SoulX 的 12–16GB 只差约 1.5–2 倍。
  前一版"增量 2.5GB / 便宜 5 倍"的说法基于错误的复用假设，已作废。

**SoulX 的 12–16GB + GPU 互斥 + 裁依赖工程量，买的是"能力"不是"音质"**：
只有路线 B（填词唱、无源干声）才需要它——RVC 是转换器，**没有源干声就无从转换**（见 §3.1）。
纯 SVC 曲库场景下 SoulX 无额外收益，却要付互斥代价。

**真正的瓶颈是素材，不是引擎**（§3.1 局限二 + 检索库那条叠加）：
现有 ~102s 落在官方 FAQ Q10 的"1–2min 成功经验不可复现"档。
**素材先过 5–10min 硬下限（§9 step 0 分层口径），歌声素材再往上加——比在 RVC / SoulX / Applio 之间纠结重要得多。**

## 6. 本机硬约束（RTX 5060 8GB / sm_120）

- **torch 版本钉子**：SoulX `requirements.txt` 钉 `torch==2.2.0`，**不支持 sm_120**，
  必须换 cu128 构建（torch 2.7+）。与 §11.3 记录的 GS 坑同源。连带风险：
  - `sageattention==1.0.6` 需编译，对新架构支持不确定（可尝试去掉，走普通 attention）；
  - `nemo_toolkit==2.6.1`（Parakeet ASR）+ `funasr`（Paraformer）很重，
    **SVC 模式用不到 ASR，可裁**（SVS 模式才需要歌词转写）。
- **onnxruntime 系分离模型慎选**：§11.3 已记录 ort-gpu 的 CUDA EP 在 DLL 版本不匹配时
  **原生崩进程、Python 捕获不到**。`audio-separator` 的 MDX 走 onnxruntime，
  官方只标 CUDA 11.8 / 12.2 → 在 5060 上有风险。
  **优先 PyTorch 系分离**（MSST 的 BS-Roformer / Mel-Roformer，或 SoulX preprocess 自带的
  `mel-band-roformer-karaoke` + `dereverb_mel_band_roformer`），torch cu128 一并解决。
- **输出 24kHz**：SoulX `config.audio.sample_rate = 24000`。QQ 语音走 silk，24k 够用；
  但别指望 44.1k 录音室音质。RVC 翻唱一般选 48k，重采样到 QQ 口径即可。
- **模型体量（2026-11-02 修正：此前按 config 推算错了）**：
  原先写"约 3–4 亿参数、fp16 权重 <1GB、比 GS 轻"，**与权重实际大小矛盾，作废**。
  实际 `model.pt` = **2.62GB**（SVS）、`model-svc.pt` = **2.60GB**（SVC），
  第三方实测显存 **SVS ≈5.4GB / SVC ≈4.3GB**，**比 GS 重，不是轻**。
  config 是 `hidden_size=1024 / num_layers=22 / num_heads=16`、`n_steps=32, cfg=3`；
  参数量推算不足以推出落盘体积（ckpt 含 optimizer/EMA 等），**以后一律以文件实测为准**。

## 7. QQ 通道约束

- **普通用户语音 60s 上限**（会员 3min / 超会 5min，且长语音不支持转文本、仅手机能发）。
  机器人经 API 发 record 能否超 60s **需实测，不要假设**。
- **产品形态建议：清唱一段副歌（30–60s）**。正好落在限制内，也符合群聊节奏
  （整首歌在群里是刷屏）。整首歌 → 走 mp3 文件 / 音乐卡片，不走 record。
- 复用 §8 的教训：**语音不带引用段**（QQ"引用+语音"气泡播不了，反复发还可能触发风控）。唱歌同理。
- 同文去重（`_is_dup_send`）对唱歌要按 `song_id` 而非文本，否则同一首歌副歌重唱会被误判刷屏；
  进行中请求的去重（in-flight）归 §5 并发护栏管。
- **版权**：翻唱现有歌曲涉及词曲著作权 + 原唱表演者权；角色音色本身是变声器产物、来自 B 站音轨。
  群里私域自娱风险低，**不要公开发布 / 不要商用**。

## 8. 验收方法（沿用 §9 的方法学，别再踩单次采样的坑）

- **多次采样取均值**（§9 教训 1：同配置三次合成底噪 p10 差 30dB，单次采样会把运气当改进）。
- 指标三件套（2026-11-03 评审修：按路线分指标）：
  - **说话人余弦**（ERes2NetV2，与 GS 验收同一把尺，可直接对比 0.85–0.89 的说话基线）——A2 主判据；
  - **F0CORR / F0RMSE**（SoulX EVAL 口径）——**路线 B（SVS）的指标**；A2/RVC 输出 F0 按构造跟随源，
    这组数只量 F0 提取链，量不出"唱功"，不进 A2 判据；
  - **咬字 CER**（现有 SenseVoice 回验，§11.1 流程）——**先测原曲干声的 STT 作对照基线**，
    否则会把"唱歌导致 STT 变差"误判成"转换咬字差"；
  - A2 的第三判据是**听感 artifacts**（电音 / 哑 / 破），只能人耳——与下方止损线配套。
- **关卡 0（2026-11-03 评审重定位：路线 B 门前，go/no-go，半天；路线 A 不经过它）**：
  拿 GS 的 `voices/` 参考 + 一首歌干声，跑 SoulX-SVC，听 + 量余弦。
  **余弦掉到 0.5 以下、或听感"不像本人" → 路线 B 作罢，不要调参硬救**
  （§11.2 范式结论：分布外音色靠 zero-shot 赌运气是错的路）。
  本机实测数字（分离耗时 / 转换 RTF / 峰值显存）不挂在这里，**提前到 §9 step 1 与 RVC 一并量**。
- 关卡 1：3 首歌 × 3 seed，确认稳定性（不是挑最好的一次）。
- **止损线（2026-11-03 评审补）**：关卡 1 两轮迭代（含补素材重训）后，余弦 / 听感仍不过线
  → 歌唱特性整体搁置、只留调研结论，不再投入（防无底洞）。
- **验收口径（2026-11-03 拍板）**：产品验收线 = 拟人标准（§10.1：不破音 + 音色可辨 + 有唱歌起伏）；
  本节余弦 / CER 数字是诊断仪器，不是上线门槛。素材第一版用说话素材先训
  （选歌 + 移调兜底高音区），歌声素材之后补。
- 关卡 2：接 QQ 实发，确认时长 / 播放 / 风控。

**异步发送形态（回答"是工具直发还是 LLM 发"）**：**工具线程直发，不经 LLM**。

出现在 LLM 轮次结束之后，且没有任何新的模型调用。

**并发护栏（有效的部分）**：群消息在 `gateway/dispatch.py` 的**单条串行 worker 线程**里跑
ToolLoop ⇒ 两条消息本身不并发（副作用：库内点歌同步转换 7–8s，这期间下一条消息排队）；
`_SING_BUSY`（TTL 900s，`acq:`/`song:` 两 namespace）挡重复产能占用；`_INFLIGHT` 按归一
歌名做 single-flight；`_SEP_LOCK` 让分钟级分离全局单飞；出站还有 napcat 同文去重
（10:11:37 那条"系统判重，跳过了"就是它，属预期行为不是 bug）。

**真缺陷：同一份 `plugin.py` 在一个进程里被装载两次 ⇒ 两个 RVC worker 单例。**
`omni_core/tools/loader.py` 用 `_MODULE_PREFIX + name`（`_omni_plugin_voice`）**按文件路径**
装载插件；而 `sing_acquire._worker_action` / `song_source` 按**包名**
`from plugins.voice import plugin` 取用 ⇒ 同一文件 exec 两遍、两个 module 对象、
**两份 `_SING_WORKER`**。在线链路恰好跨在两份上：切副歌/定 key 走包名那份、转换走 loader 那份。
日志实证（temp/omniagent.log，单网关进程 38992）：10:06:20 就绪 pid 44632 → **没有被回收**，
10:14:53 又就绪 pid 9104 ⇒ **两个 RVC 子进程共存约 14 分钟**；两条相隔 5s 的回收日志
（10:20:24 空闲 325s / 10:20:29 空闲 329s）对应两个实例，且各自的 `_last_used` 正好是
10:14:59（F0/切副歌）与 10:15:00（转换）——与"两份各干一段"完全吻合。
代价：显存/内存双份、`_lock` 的"全进程只有一路 GPU 唱歌"不变式失效（异步补投与下一条
库内点歌可真并发抢卡）、在线链路白付一次 ~6s 冷启动、两个空闲回收线程各杀各的。

**修法（不留双路径）**：新增 `plugins/voice/sing_runtime.py`，把**跨模块共享状态**整体搬过去
——`_SingWorker` 类 + 唯一的 `_SING_WORKER` 实例、声库/解释器/仓库根路径、超时与 idle 常量、
`_SING_DIR`、以及 `voice_cfg()`（voice.yaml 读取的唯一实现，`plugin.py` 的 `_cfg` 只是它的名字）。
该模块**只按包名 import**，永远不经 loader ⇒ 全进程只有一份。依赖方向单向
`plugin.py → sing_runtime`（反向会把二次装载引回来）。`plugin.py` 从 668 行缩到 405 行，
唱歌段只剩一行指针注释 + startup/shutdown 两处装配。
护栏用例：`tests/test_sing_acquire.py::test_double_import_shares_one_sing_worker`
（模拟 loader 按路径二次装载，断言 `second._SING_WORKER is sr._SING_WORKER is vp._SING_WORKER`）。

**仍开放**：① 关卡 2（群里真发）待用户 @ 点歌；② **不同措辞**在 ~80–150s 窗口内仍可能各下一遍
（`_SING_BUSY`/`_INFLIGHT` 都按归一点歌话做键，跨措辞不合并）；③ 这些键都是**进程内内存态**，
若以后 web 面板（后端进程 4348）也能触发唱歌，两边互不可见——同歌并发要收就得落盘或用文件锁；
④ L2 成品缓存；⑤ `send_sing` 与 `send_voice` 合并；⑥ §11 开放项 ①（整首 stem 转换病理性慢）原样保留。
